# 실데이터 증분 집계 검증

운영 Bronze와 Silver는 읽고, `scratch/new-day-20261001`의 실험 표만 갱신한다. 기존 사본은 과거 운영 Silver를 복제한 것으로 30초 기준을 소급 적용한 분석 결과가 아니다.

## 실행 순서

1. 엔진과 이미지, 디스크와 절전 방지 상태를 확인한다.
2. 첫 덤프와 후속 덤프의 스테이징 파일을 확인한다. 실제 청취가 없는 빈 덤프는 입력으로 쓰지 않는다.
3. 작은 Spark 중단 주입과 재개 테스트를 통과한 코드로 실험한다.

```bash
./scripts/spark_run.sh -m 24g -- python scripts/drills/new_dump_increment.py \
  --dump listenbrainz-dump-2690-20261001-000003-incremental \
  --work new-day-20261001 --resume \
  --next-dump listenbrainz-dump-2728-20261018-000003-incremental \
  --next-work new-day-20261018
```

각 입력은 최초 반영과 재실행을 거친다. 병합 시작 버전과 단계 표식을 먼저 저장하고, 표식이 있는 정확한 병합 커밋을 찾으면 다시 병합하지 않는다. 격리 저장과 CDF 집계는 그 뒤에 이어 간다. 예상 밖의 커밋이 있거나 품질 기준과 입력 순서가 바뀌면 중단한다. 프로세스 간 파일 잠금은 Linux 테스트 컨테이너에서 사용한다.

결과 파일은 임시 JSON을 완성한 뒤 교체한다. 각 단계에 Silver와 집계의 ID, `versionAsOf`로 읽은 버전과 파일 목록을 남긴다. 집계가 처리한 Silver 버전과 ID가 일치해야 한다. 입력 건수와 격리 건수, 병합 결과 및 최종 행 수를 검사하고 재실행 시 삽입과 갱신이 0인지 확인한다.

## 독립 대조

Spark 실행이 끝나면 호스트에서 DuckDB 대조를 실행한다. 아래 데이터 루트는 실제 경로로 바꾼다.

```bash
PYTHONPATH=src ./venv/Scripts/python.exe scripts/drills/verify_increment_counts.py \
  --data-root "C:/data/flux-data" --work new-day-20261001
```

각 단계에서 저장한 파일 목록만 읽으며 최신 파일을 다시 탐색하지 않는다. 같은 물리 파일 집합은 계산을 재사용하고 각 결과에 해당 단계의 정확한 버전을 기록한다. 원본 스테이징을 파이썬으로 다시 판정해 격리 사유별 건수도 비교한다. 저장된 첫 덤프의 독립 예상값이 있으면 삽입과 갱신 건수를 대조한다.

Silver 전체를 사용자와 MSID별로 다시 센 뒤 집계와 FULL OUTER JOIN으로 모든 키의 횟수를 비교한다. 누락된 키, 잘못된 횟수, 중복 집계 키, NULL 키와 양수가 아닌 횟수는 실패다. 총합 일치만으로 통과시키지 않는다. 결과는 실험 폴더의 `oracle.json`에 저장한다.

두 덤프 실험의 통과는 기존 계획의 7일 연속 증분 검증이나 성능 목표의 완료를 뜻하지 않는다. 서로 떨어진 날짜의 덤프를 사용하므로 중간 구간의 수집 완료도 의미하지 않는다. 절전 방지 도우미는 작업 종료 또는 중단 시 해제한다.
