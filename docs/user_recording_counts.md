# 사용자별 곡 청취 횟수

> 새 Silver는 사용자 이름+MSID+UTC 청취 월별 횟수로 전환한다. [월별 Silver 전환](#월별-silver-전환)이 최신 규칙이며, 아래 전체 기간 집계 설명은 기존 모델의 이력이다.

Silver의 `user_recording_counts`는 날짜 구분 없이 `user_id + recording_msid`당 한 행을 저장한다.

| 컬럼 | 의미 |
| --- | --- |
| `user_id` | 사용자 식별자. 이름이 바뀌어도 같은 사용자로 묶는다 |
| `recording_msid` | ListenBrainz의 제출된 곡 정보 식별자 |
| `play_count` | 품질 검사와 동일 청취 중복 제거를 통과한 청취 횟수. bigint |

같은 사용자의 같은 MSID를 합친다. 다른 사용자나 다른 MSID는 별개다. MBID 유무를 조건으로 거르지 않으므로 정제와 동일 청취 중복 제거를 통과한 모든 상세 행이 집계에 포함된다. MBID 컬럼 자체가 없어도 계산할 수 있다. 기존 MSID 전수 비결측 실측을 전제로 하며 MSID가 누락된 입력을 위한 임의 식별자 생성 규칙은 두지 않는다.

MBID와 곡명 등의 메타데이터는 상세 `listens_normalized`에 보존한다. 같은 MSID에서 MBID만 변경되면 횟수는 그대로다. 서로 다른 MSID는 같은 MBID가 연결되어 있더라도 현재 집계에서 합치지 않는다. 같은 곡의 MSID들을 연결하는 판단은 후속 매칭 단계에서 별도로 설계한다. 이 표의 집계 단위는 녹음 자체가 아니라 제출된 곡 정보의 ID다.

## 갱신

`silver_build.py`와 `silver_increment.py`는 상세 Silver 저장이 끝난 뒤 이 표를 갱신한다. 실제 재생 시간 `ms_played`가 숫자로 확인되고 30,000밀리초 미만인 행은 먼저 격리한다. 정확히 30초인 값과 시간이 없는 기록은 유지하며, 곡 길이인 `duration_ms`로 대체하지 않는다. Bronze 원문은 보존한다. 집계는 이미 동일 청취 중복을 제거한 `listens_normalized`에서 계산한다. 새 청취가 하나 늘면 해당 횟수가 하나 늘고, 처음 보는 사용자와 곡 조합은 새 행이 된다.

최초 생성 때는 상세 Silver 전체를 한 번 집계한다. 이후에는 마지막으로 처리한 Silver 버전 다음부터 최신 버전까지의 Delta Change Data Feed(CDF)를 읽는다. CDF는 삽입, 삭제와 수정 전후의 행을 구분한다.

- 삽입과 수정 후 행은 해당 사용자와 MSID에 +1을 반영한다.
- 삭제와 수정 전 행은 -1을 반영한다.
- 변경분을 사용자와 MSID별로 합산해 기존 행에는 가감하고, 새 조합은 생성한다. 합계가 0인 조합은 삭제한다.
- MBID가 없는 행도 같은 방식으로 가감한다. MSID가 수정되면 이전 MSID에서 차감하고 새 MSID에 가산한다. MBID만 수정되면 그룹별 순변화량은 0이다.

가감과 처리 위치를 같은 집계 Delta 커밋의 userMetadata에 저장한다. 커밋 전에 실패하면 둘 다 반영되지 않고, 커밋 직후 실패하면 재실행에서 처리한 버전을 건너뛴다. 횟수 변화가 없는 변경도 메타데이터 커밋으로 처리 위치를 전진시킨다. 원본 표의 고유 ID와 집계 키도 저장해 다른 표나 다른 집계 단위의 처리 위치를 잘못 이어 읽지 않는다. 기존 Spark 세션의 커밋 메타데이터 설정은 실행 후 복원한다.

증분 집계에서는 상세 Silver 전체를 다시 집계하지 않는다. CDF 변경분을 읽고 집계 대상과 MERGE한다. 대상 파일의 탐색과 재작성 비용은 있으며 전체 집계 표를 전혀 읽지 않는다는 뜻은 아니다. 단일 실행자를 전제로 하며 같은 집계에 대한 병렬 갱신은 지원하지 않는다.

상세와 집계는 각각 별도의 Delta 트랜잭션이므로 집계가 실패하면 상세만 최신일 수 있다. 아래 명령은 마지막 처리 위치에서 이어 간다. 운영 Silver에는 CDF가 활성화되어 있어야 한다.

```bash
./scripts/spark_run.sh -m 12g -- python scripts/pipeline/silver_user_recording_counts.py
```

처리 위치가 없거나 집계 키가 다른 옛 집계, 교체된 원본, 보존 기간이 지나 사라진 CDF는 자동으로 전체 재집계하지 않고 오류로 알린다. 이 경우 명시적으로 초기화한다. MBID 기준으로 생성한 기존 표는 버전 숫자가 같아도 이어 쓸 수 없으며 아래 명령으로 MSID 기준으로 한 번 재생성해야 한다. 전체 Silver 생성 스크립트도 집계를 초기화한다.

```bash
./scripts/spark_run.sh -m 12g -- python scripts/pipeline/silver_user_recording_counts.py --rebuild
```

이 명령은 기존 상세 Silver를 원본으로 사용한다. 30초 미만 제외 규칙을 과거 데이터에 적용하려면 상세 Silver부터 다시 생성해야 한다. 코드 변경만으로 운영 데이터가 바뀌지는 않는다. 기존 Gold와 탐색 화면은 상세 기록 기반으로 유지되며 이 집계로 자동 전환되지 않는다.

## 조회

SQL 실행기에서 `{user_recording_counts}`로 읽을 수 있다.

```sql
SELECT recording_msid,
       count(*) AS listener_count,
       sum(play_count) AS play_count
FROM {user_recording_counts}
GROUP BY recording_msid;
```

한 MSID 안에서는 행 수가 청취자 수다. 실제 같은 곡이 여러 MSID로 나뉘어 있으면 행 수를 단순 합산하지 않고 후속 매칭 뒤 사용자의 고유 수를 계산해야 한다. 여러 곡이나 아티스트를 합칠 때는 같은 사용자가 다시 등장하므로 `count(DISTINCT user_id)`로 계산한다. 이 표는 반복 청취의 영향과 청취자 규모를 구분하게 하며, 반복 청취를 조작으로 판정하거나 삭제하지 않는다.


## 재생 시간 값의 해석

파이썬과 Spark는 같은 30초 기준과 숫자 문자열 문법을 사용한다. 실제 숫자와 일반 십진수 및 소수, 부호와 지수 표기의 문자열을 해석한다. 숫자로 확인된 음수도 30초 미만으로 격리한다. NULL, 빈 문자열과 해석 불가 문자열, 불리언과 객체 및 배열은 시간을 추정하지 않고 유지한다. 밑줄 구분 숫자, 전각 숫자와 f 접미사도 숫자 문자열로 인정하지 않는다. 경계값과 값의 유형을 포함한 공통 입력 26개에서 두 구현의 실제 판정 일치를 Spark로 확인했다.

## 분석 목적과 현재 검증 범위

짧은 재생 격리, 반복 청취 집계와 같은 곡 연결은 서로 다른 문제를 다룬다.

- 짧은 재생 격리는 건너뛴 재생을 제외하기 위한 정제다. [Spotify 공식 집계 기준](https://support.spotify.com/us/artists/article/how-your-streams-are-counted/)을 참고해 30초를 사용한다. 실제 청취 여부를 완벽하게 증명하는 기준은 아니다. 곡 자체가 30초보다 짧아도 예외를 두지 않으며, 재생 시간이 없는 기록은 판단하지 않고 유지한다. RM 사례의 해당 사용자 기록은 Last.fm importer에서 왔고 ms_played가 없어 이 필터의 대응 대상이 아니다.
- 반복 청취는 삭제하지 않는다. 두 번 들으면 play_count는 2다. Gold에서는 청취자 수와 청취 수를 함께 제시하고 순위는 청취자 수로 매기는 것이 결정된 방향이다. 한 사용자의 반복이 순위를 압도하는 RM 사례에 대한 대응이다. Gold 순위 변경은 구현됐으며 별도 전체 재생성에서도 검증했다. 청취자 수는 계정 수이며 한 사람이 여러 계정을 사용했는지는 데이터로 구분할 수 없다.
- 같은 곡 연결은 서로 다른 MSID에 같은 곡이 등록된 문제를 다룬다. AI가 후보 유형을 먼저 분류하고 사람이 사례를 읽어 판단한 뒤 보정 규칙을 보강한다. 이름 정규화로 겹친 후보를 바로 같은 녹음으로 확정하거나 자동 병합하지 않는다. play_count와 별개로 필요한 단계다.

아래는 중단 당시 기록이다. 증분 검증의 후속 완료 상태는 다음 문단을 참고한다. 증분 가감과 재실행 시 중복 가산 방지 로직은 당시 구현했고 검증 중이었다. 작은 Spark 테스트와 별개로, 실데이터 증분 결과를 전체 재계산 결과와 사용자+MSID 키마다 대조하는 검증은 아직 완료하지 않았다. 10월 1일 덤프 4,147,399건은 운영 Bronze가 아닌 scratch/new-day-20261001 실험 사본에 적재했으며, 실제 Silver 병합과 재실행 검증은 중단 상태다. 기존 실험의 품질 판정은 당시 10초 기준이므로 재개 시 30초 기준으로 결과와 기준을 확인한다.

2026-10-18 운영 Bronze 전체를 읽기 전용으로 다시 측정했다. 155,713,649건 중 숫자 ms_played는 43,453,540건, 10초 미만은 1,187,137건, 30초 미만은 1,318,299건이다. 기준 변경으로 추가 격리되는 구간은 10초 이상 30초 미만인 131,162건이다. 이 측정은 다른 품질 규칙과 동일 청취 중복 제거를 적용하기 전 원본 건수다. 운영 Silver를 소급 재생성하지 않았다.


기존 참고 실측에서 Silver의 서로 다른 MSID는 21,170,586개이고, 소문자와 앞뒤 공백만 정리한 아티스트와 곡명 쌍은 11,985,247개다. 이름 쌍 수가 MSID 수보다 약 43.4% 적지만 이를 확정된 동일 곡 비율로 해석하지 않는다. 곡 길이가 30초 미만인 Bronze 기록은 기존 참고 실측 49,455건이며, 이런 곡을 끝까지 들어도 실제 재생 시간이 30초 미만이면 격리된다. 두 참고 실측은 이번 변경에서 다시 측정하지 않았다.

2026-10-19 후속 상태: 두 덤프와 각 재실행의 고정 버전 키별 대조를 완료했다. 이어 30초 기준 별도 전체 재생성에서 41,724,434개 사용자+MSID 키의 횟수가 독립 재계산과 모두 일치했다. 합계는 Silver와 같은 150,385,259다. 새 Silver 원본 ID와 처리 버전으로 초기화했고 CDF도 검증했다. 운영 경로는 교체하지 않았다. [전체 결과](rebuild_30seconds.md)를 참고한다.
# 월별 Silver 전환

2026-10-19부터 새 분석 단위는 `user_name + recording_msid + listened_month`다. 아래 전체 기간 `user_id + MSID` 집계는 기존 상세 모델을 설명하는 이력으로 보존한다. 새 월별 출력에는 `listens_normalized`와 기존 전체 기간 횟수 표를 복제하지 않는다. 원본 Bronze와 이전 검증본은 별도로 보존한다.

`scripts/pipeline/silver_monthly.py --bronze <Bronze경로> --output <별도월별Silver경로>`는 세 Delta 표를 관리한다.

| 표 | 저장 정보 |
| --- | --- |
| `monthly_user_recordings` | 사용자 이름, MSID, UTC 청취 월, BIGINT play_count |
| `recording_metadata` | MSID, 곡명, 아티스트명, recording MBID, artist MBID 배열, MBID 출처의 고유 조합 |
| `invalid_listens` | 품질 규칙 위반 원본과 사유 |

품질 판정(30초 미만 포함), 동일 사건 중복 제거, 월별 횟수 계산 순서다. 재생 시간이 없으면 유지하고 MBID가 없어도 횟수에 포함한다. MSID가 없으면 임의의 공통 곡으로 합치지 않고 실행을 중단한다. 월별 집계만으로 일별 또는 주별 지표를 복원할 수 없으며 해당 분석은 Bronze에서 다시 만들어야 한다. 사용자 이름은 사람 식별자가 아니다.

증분은 Bronze CDF에서 변경 사건을 찾고 고정된 이전 및 이후 원본 버전에서 동일 사건의 후보를 조회한다. 사건 키는 사용자 이름+청취 시각+MSID이며 품질과 기존 승자 선택 규칙을 다시 적용한다. 이전 및 이후의 월별 기여 차이만 더하므로 같은 사건의 다른 덤프 재도착이나 재실행은 중복 가산하지 않는다. 삭제와 수정도 이전 기여 감소 및 이후 기여 증가로 처리한다. 사건별 영구 처리 이력 표는 추가하지 않는다. Spark 중간 체크포인트는 실행 중에만 사용한다.

메타데이터는 승자가 제공한 고유 변형을 누적한다. 나중에 청취가 삭제되거나 승자가 바뀌어도 이미 관측한 변형은 남으므로 현재 청취에 쓰이지 않는 변형도 있을 수 있다. 곡 매핑 정답이나 MSID당 유일 행이 아니다. 횟수와 사전을 MSID로 바로 다대다 조인하면 횟수가 늘어날 수 있어, Gold에서는 먼저 대표 메타데이터 또는 명시적인 귀속 규칙을 정해야 한다.

각 표의 처리 상태는 Bronze ID와 버전, 키, 품질 정책 버전, 최소 재생 시간과 UTC 설정이다. 횟수 변경과 그 체크포인트는 같은 Delta 커밋에 기록한다. 세 표 사이의 단일 트랜잭션은 없으므로 `monthly_listens.ready`로 세 표의 상태 일치를 확인한다. 실제 소비자는 `pin_snapshot`이 같은 작성자 잠금 안에서 얻은 표별 버전을 사용해 `versionAsOf`로 읽어야 한다. 준비 여부를 확인한 뒤 최신 표를 읽으면 그 사이 다음 증분이 시작될 수 있기 때문이다. 표 사이에 중단되면 이미 완료한 표를 건너뛰고 미완료 표만 재시도한다. 세 표가 일치하기 전에는 전체 성공으로 보고하지 않는다.

로컬 출력의 `.writer.lock`은 이 진입점의 동시 작성자를 막는다. 강제 종료 후 남은 잠금은 작성자 프로세스 종료를 확인한 뒤 수동 해제해야 한다. 다른 경로나 다른 잠금 구현을 사용하는 작성자를 자동으로 조율하지 않는다. 입력과 출력이 같거나 부모/자식이면 거부한다. CDF가 없거나 원본 ID 또는 정책이 달라지면 임의로 이어 쓰지 않고 별도 재생성을 요구한다.

기존 전수 검증 Silver를 줄일 때는 `scripts/migrations/compact_monthly_silver.py --verified-root <기존검증루트> --output <새경로>`를 사용한다. 기존 검증 증거와 고정 ID, 버전 및 로그 해시를 확인한 뒤 읽고 새 표를 만든다. 이어 `verify_monthly_silver.py`가 DuckDB로 모든 월별 키와 횟수, 메타데이터와 격리를 대조한다. 생성 완료와 독립 검증 완료는 별도 상태다. 새 데이터는 자동으로 운영 경로에 교체하지 않는다.

현재 통합 Bronze v0에는 CDF가 없다. 초기 전환은 가능하지만 이후 덤프를 넣기 전에 대상 Bronze에서 CDF를 활성화해야 한다. 과거 버전이나 변경 이력을 보존하지 않은 구간은 소급 추측하지 않는다. 새 증분의 대규모 처리 성능은 아직 측정하지 않았다. 기존 Gold는 상세 입력에 의존하므로 월별 표를 기존 Gold 잡에 그대로 넘기지 않는다.

## 월별 Gold의 아티스트 귀속 기준

2026-10-19 결정: 해당 녹음의 공식 아티스트 크레딧에 있는 메인과 피처링 아티스트에게 청취 수를 부여한다. MusicBrainz의 recording `artist-credit`를 확인하고 제작자, 엔지니어 등 `relations`에만 있는 사람은 포함하지 않는다. 특정 인물을 전역 제외하는 규칙이 아니라 녹음별 크레딧을 확인하는 규칙이다. MusicBrainz에 기록된 크레딧을 근거로 사용하며 이 자료 자체의 오류 가능성도 남는다.

월별 Silver 사전의 실제 변형을 공식 API와 대조한 표본에서 다음 사례를 확인했다. 전체 오류 건수나 비율을 측정한 결과는 아니다.

정상 대조군인 [Bad Blood의 해당 녹음](https://musicbrainz.org/ws/2/recording/d112254a-b6a1-4993-bdd9-ea4cd0926d4b?inc=artist-credits%20artist-rels&fmt=json)은 Taylor Swift와 Kendrick Lamar가 모두 공식 artist-credit에 있다. Kendrick Lamar는 유지한다. 같은 제목의 다른 버전까지 이 결론을 일반화하지 않는다.

이번 단계는 기준 결정과 표본 조사다. Gold 구현과 데이터 교체는 하지 않았다. 원본 청취와 관측 메타데이터는 보존하고 Gold용 귀속 관계를 별도로 만든다. MBID가 없는 곡이나 공식 자료를 확인하지 못한 곡의 처리, 사전 변형 간 충돌 해결은 후속 구현 전에 정해야 한다.

## 곡 연결과 동일 청취 중복의 분리 조사

월별 Gold 구축은 보류한다. 현재 월별 Silver는 MSID별 관측 횟수이며 곡 연결과 다른 MSID 사이의 동일 청취 판별이 끝난 최종 곡 지표가 아니다. 같은 곡의 MSID를 묶는 것만으로 전체 play_count는 줄지 않는다. 같은 사용자, 같은 녹음과 같은 청취 시각인 사건을 하나로 보는 추가 규칙을 적용해야 전체 횟수가 줄어든다. 다른 시각의 반복 청취는 보존한다.

`scripts/investigations/audit_recording_identity.py`는 현재 월별 Silver와 청취 시각이 있는 상세 검증본을 DuckDB로 읽기 전용 조사한다. `--monthly-root <월별Silver> --detail <상세Delta표> --output <새조사폴더> --threads 2`로 실행한다. flux가 설치되지 않은 PowerShell에서는 먼저 `$env:PYTHONPATH='src'`를 설정한다. 입력과 겹치는 출력 경로 및 기존 조사 폴더는 허용하지 않는다. 원본 Delta 활성 파일만 읽고 전후 로그 버전과 해시가 같은지 확인한다. 조사용 DuckDB와 JSON은 원본 및 중간 산출물이므로 git에 넣지 않는다.

메모리 상한은 기본 `--memory-gb 16`이다. 첫 6GB 실행은 MBID 계산 후 이름 기준의 전체 사건 계산에서 메모리 부족으로 중단됐다. 현재 구현은 실행 중에만 유효한 숫자형 사전 키로 묶고 보고서에서 원래 식별자로 되돌린다. 서로 다른 MSID 수는 충돌 후보에서만 다시 계산해 같은 MSID 중복 차단도 유지한다. 원본의 버전과 해시는 시작 시 `snapshots.json`에 먼저 기록하며 `result.json`의 `completed`와 `source_unchanged`가 모두 참이어야 전체 완료다. 중간 파일만으로 전체 성공을 판단하지 않는다.

두 가정은 독립적으로 측정하며 감소량을 더하지 않는다.

- `mbid`: 하나의 MSID에서 관측한 비어 있지 않은 recording MBID가 하나일 때만 그 MBID를 사용한다. 같은 MBID에 여러 MSID가 연결된 후보를 조사한다. MBID가 없는 변형이 함께 있으면 해당 연결을 그 MSID에 적용하는 가정이다. MBID의 사실 정확성까지 보장하지 않는다.
- `name`: 한 MSID의 모든 변형에서 아티스트명과 곡명이 존재하고, 소문자 및 앞뒤 공백 정리 후 한 쌍일 때만 사용한다. 같은 이름 쌍에 여러 MSID가 연결된 후보를 조사한다. 서로 다른 MBID나 라이브 및 편집 버전도 섞일 수 있어 실제 삭제 규칙으로 승인한 것이 아니다. 접미사 제거와 유사 문자열 매칭은 하지 않는다.

사전은 MSID당 한 행인 후보 매핑으로 먼저 줄여 횟수의 다대다 증식을 막는다. 각 후보에 대해 월별 사용자+곡 키의 횟수와 상세의 횟수를 전부 대조하고 불일치 시 중단한다. 기존 사용자+MSID+시각 중복이 남아 있어도 중단해 다른 MSID의 중복과 혼동하지 않는다. 같은 시각의 정의는 원래 저장된 시각의 정확한 일치이며 초 또는 분 단위 반올림이나 시간 허용 범위를 적용하지 않는다.

`tests/test_recording_identity_audit.py`는 메타데이터 반복과 MBID 충돌, 정상 반복 청취와 다른 사용자 및 다른 월, 이름만 같고 MBID가 다른 경우, 월별과 상세 불일치, 기존 같은 MSID 중복을 검증한다. 이 조사는 사용자 이름을 실제 사람으로 확정하거나 서로 다른 계정을 통합하지 않는다.

### 조사 실행의 현재 상태

2026-10-19 점검에서 두 번째 실행의 MBID 결과 13개 수치는 첫 실행과 같았고 291.06초가 걸렸다. 이름 기준 결과는 저장되지 않았으며 실행 프로세스도 종료된 상태다. `result.json`은 `completed=false`이고 종료 시 원본 검사 항목도 없으므로 전체 조사 완료로 표시하지 않는다. 두 번째 실행의 종료 원인은 확보된 결과만으로 확정하지 않는다. 별도 사후 검사에서 시작 시 기록한 세 입력의 Delta 로그 버전과 해시는 현재 값과 같았다. 조사 테스트 6개는 통과했다. 이름 기준 전체 조사와 후보 검수는 [남은 작업](status.md)으로 유지한다.
