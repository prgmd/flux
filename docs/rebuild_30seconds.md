# 30초 기준 전체 재생성

2026-10-19 별도 경로의 전체 생성과 독립 검증을 완료했다. 운영 데이터는 교체하지 않았다.

## 입력과 출력

- 입력: 운영 Bronze `raw_listens` v0, 155,713,649행, 293개 파일, 27,786,350,920바이트. 기존 31개 덤프만 포함하며 추가 두 덤프의 실험 사본을 합치지 않는다.
- 운영 비교 기준: Silver v0 151,192,624행, 팩트 v0, 아티스트 차원 v8. 실행 전후의 표 ID·버전·전체 JSON 커밋 로그 해시를 기록한다.
- 별도 결과: `flux-data/rebuild-30s-20261019`. 운영 표 교체나 VACUUM은 하지 않는다.
- 실행은 전용 Docker 볼륨에서 진행하고 완료한 표를 위 호스트 경로에 내보낸다. 운영 경로는 컨테이너에 읽기 전용으로 연결한다.

먼저 시스템과 화면 절전 방지를 설정한다. 작업 종료 시 해제한다. 불변 Bronze 사본은 `scripts/drills/cache_silver_readonly.py`로 파일별 크기와 SHA-256을 대조한 뒤 사용한다. 아티스트 차원은 기존 파일과 로그 이력을 사본으로 준비한다.

## 생성

`scripts/migrations/rebuild_playback.py`는 기존 생산 함수를 다음 순서로 실행한다.

1. 품질 격리(숫자로 확인된 재생 시간 30초 미만 포함) 후 동일 청취 중복 제거를 거쳐 Silver와 격리 표 생성.
2. CDF가 활성화된 새 Silver에서 `user_recording_counts`를 `rebuild=True`로 초기화.
3. Gold 팩트 생성 및 복사한 아티스트 차원의 필요한 자리 행 보강.
4. 날짜·사용자 차원 재생성.
5. 기존 일별 마트와 청취 수 증가율 기반 주간 급상승 생성.
6. 새 일별·주별 청취자 순위 및 최대 계정 비중 마트 생성.

재생 시간이 없거나 숫자로 해석되지 않는 기록은 짧은 재생 사유로 격리하지 않는다. 원본의 30초 미만 건수와 Silver 감소량은 중복 제거 관계 때문에 반드시 같지 않다. 월별 사용자 이름 해시 16버킷 배치와 CDF를 유지한다. 새 원본 ID에 옛 집계의 처리 위치를 재사용하지 않는다.

컨테이너에서 `/production`은 운영 읽기 전용, `/work`는 검증한 Bronze·차원 사본과 출력용 볼륨, `/export`는 호스트의 별도 결과 경로로 연결한다.

```bash
python scripts/migrations/rebuild_playback.py \
  --production-root /production --work-root /work --export-root /export
```

단계별 완료와 표 ID·버전·로그 해시 및 경과 시간을 `rebuild.json`에 원자적으로 기록한다. 같은 볼륨으로 재실행하면 완료한 표의 상태를 확인한 후 다음 단계부터 이어간다. 기록된 완료 표가 달라졌다면 멈춘다. 완료 표가 아직 호스트에 전부 복사되지 않았더라도 재실행 시 다시 내보낼 수 있다. 한 결과 경로에는 동시에 여러 생성 작업을 실행하지 않는다.

## 독립 검증

예전 `compare_rebuild.py`는 기록 번호만 바뀌는 이전 작업용으로 내용과 행 수 동일을 요구한다. 이번에는 정책 변화로 행 수 감소가 정상이므로 그 조건을 그대로 적용하지 않는다.

`scripts/migrations/verify_playback_rebuild.py`는 호스트 DuckDB로 운영 Bronze에서 품질 사유와 남아야 할 후보를 독립 계산한다. 품질 검사를 먼저 한 뒤 출처·아티스트 수·덤프·기록 번호의 우선순위로 승자를 고른다. 예상 승자와 실제 Silver의 모든 출처 키 및 사용자·곡·청취 시각·MBID 선택·아티스트 배열을 대조한다. 전체 Silver 컬럼에 대한 바이트 단위 비교를 뜻하지는 않는다.

이어 다음을 전수 대조한다.

- 모든 격리 키와 사유, 모든 사용자+MSID별 횟수와 중복 키.
- Silver를 펼친 예상 팩트의 청취+아티스트 키와 팩트 값.
- 일별 합계·고유 청취 사건 수·시점 이름과 주간 급상승.
- 기간별 청취 수·고유 계정 수·순위·최대 계정 횟수와 비중 및 커버리지.
- 날짜 범위와 속성, 사용자별 이름·첫/마지막 청취·횟수.
- 고아 아티스트, NULL 식별자, Silver 중복 키와 한 사용자의 한 달이 여러 파일에 갈라졌는지.
- Silver CDF와 횟수 집계·팩트·새 마트의 원본 ID 및 처리 버전.

표마다 활성 파일 목록과 버전을 고정하고 종료 시 그대로인지 확인한다. 운영 원본의 로그와 ID도 재확인한다. 파일이 없는 정상적인 빈 Delta 표는 로그의 스키마로 읽는다. 실수로 옛 비활성 Parquet 파일을 함께 읽지 않는다.

```bash
venv/Scripts/python scripts/migrations/verify_playback_rebuild.py \
  --production-root C:/Users/SSAFY/Desktop/jjh/flux-data \
  --rebuild-root C:/Users/SSAFY/Desktop/jjh/flux-data/rebuild-30s-20261019
```

`--prepare-only`로 원본의 예상 결과 계산을 생성과 병행할 수 있다. `oracle.duckdb`에는 독립 중간 결과, `verification-snapshots.json`에는 고정 입력, `verification.json`에는 각 대조 결과가 저장된다. 표 생성 완료와 검증 완료는 다르며 마지막 `ok: true`와 운영 불변 감사까지 확인해야 한다. 데이터를 저장소에 커밋하지 않는다.

## 도구 검증

경로 겹침과 로그 변경 탐지, 30초 경계·음수·누락·텍스트·불리언 처리, 잘못된 값·누락·중복 키 탐지 및 빈 Delta 읽기를 검사하는 순수 테스트를 추가했다. `tests/test_spark_playback_rebuild.py`는 임시 Bronze에서 전체 생성과 재개를 실행하고 내보낸 모든 표를 DuckDB 검증기로 대조한다. 격리될 높은 우선순위 후보가 정상 후보를 밀어내지 않는지도 검사한다.

```bash
venv/Scripts/python -m pytest tests/test_rebuild_playback.py tests/test_playback_rebuild_oracle.py -q
MSYS_NO_PATHCONV=1 docker run --rm \
  --mount "type=bind,source=$(pwd -W),target=/opt/flux,readonly" \
  flux-spark:latest python -m pytest tests/test_spark_playback_rebuild.py -m spark -q -p no:cacheprovider
```

개발 중에는 컨테이너에 현재 소스와 테스트를 읽기 전용으로 마운트해 이미지에 남은 옛 코드가 실행되지 않게 한다. 전체 재생성 전후 수치가 달라졌다는 사실만으로 성능 개선이나 대표성 개선을 주장하지 않는다.

## 추가 덤프 포함 Silver 전용 재생성

기존 결과의 입력은 운영 Bronze 155,713,649건이었다. 추가 두 덤프 6,966,148건을 포함하는 별도 통합 입력은 162,679,797건이다. 기존 표의 재실행 이력에서 활성 파일만 선택하고 파일별 해시로 사본을 확인한다. 원본 표는 수정하지 않는다.

재생성 도구의 `--silver-only`는 Silver 상세, 격리 표와 사용자+MSID 횟수만 생성하고 종료한다. Gold가 없는 새 출력에서 실행하며 기존 전체 모드와 범위를 바꿔 재개하면 거부한다. 품질 격리 후 동일 청취 중복 제거, 반복 횟수 집계 순서를 유지한다. 짧은 재생 제외로 남아야 할 중복 후보가 달라질 수 있어 옛 Silver에서 단순 삭제하는 대신 통합 Bronze에서 다시 선택한다.

검증기의 `--silver-only --bronze-root <통합입력루트>`는 별도 통합 Bronze를 독립 계산하고 Silver, 격리와 모든 사용자+MSID 횟수를 대조한다. 고정 입력 버전과 운영 원본 불변도 확인한다. 범위와 입력은 결과 JSON에 남긴다. 추가분을 포함한 Gold는 이 Silver 검증 뒤 별도 작업으로 수행한다. 최신 통합 결과는 아래와 같다.

전량 원본 재해석 실행은 일시정지 후 Silver 커밋 전에 종료됐다. 미커밋 파일을 결과로 인정하지 않고 기존 30초 정책 전수 검증본의 해시 확인 사본에 추가 두 덤프를 같은 품질 및 증분 규칙으로 반영해 복구했다. 첫 덤프는 삽입 4,147,399건, 갱신 0건이고 두 번째는 삽입 2,818,705건, 갱신 44건이다. 집계는 복구된 전체 상세에서 초기화했다. 기존 검증본의 생성 시각은 보존되므로 모든 행의 생성 시각이 하나의 실행 시각이라는 뜻은 아니다.

생성 경로와 별개로 통합 Bronze 전체에서 계산한 독립 예상 결과와 실제 격리, Silver 및 모든 사용자+MSID 횟수를 전수 대조했다. 세 대조 모두 불일치와 중복 키 0건이다. 청취 사건 키 중복, 빈 식별자, 잘못된 횟수, CDF 비활성, 집계 원본 ID 및 버전 오류도 모두 0이다. 운영 원본 불변 감사도 통과했다. Silver 주요 값 대조는 710.0초, 횟수 대조는 202.5초이며 이를 생성 성능으로 해석하지 않는다. 복구 실행은 CPU 4개로 제한했다.

운영 경로는 교체하지 않았다. 이 통합 입력의 Gold 팩트와 마트는 실행하지 않았다. 앞 절의 Gold 수치는 기존 덤프만의 검증본이므로 이 Silver와 같은 입력 범위의 결과로 사용하지 않는다. 같은 곡의 다른 MSID를 연결하는 작업도 별도이며 이번 중복 제거 키를 넓히지 않았다.


### 실제 기록 표본 검수

전수 대조 뒤 실제 원본과 결과를 추적했다. 29,999ms 4건은 격리됐고 30,007ms, 30,013ms, 30,079ms와 30,082ms 4건은 유지됐다. 추가 두 덤프와 기존 구간의 재생 시간 누락 6건도 유지됐다. 선택한 출처 14건의 실제 보존 여부는 독립 예상 승자와 같았고, 보존된 표본 10건의 곡명과 아티스트명은 원본과 같았다. 정확한 30,000ms 경계는 소형 테스트에서 별도로 검사했다.

반복 상위 5개 사용자+MSID의 상세 횟수는 집계와 같고 각각 모두 서로 다른 청취 시각이었다. 최대 사례는 RM의 LOST! 42,717회, 352개 청취 일자다. 이 사실은 기록된 사건이 서로 다른 시각이라는 뜻이며 실제 사람의 재생 행동이나 조작 여부를 입증하지 않는다. 반복 자체를 삭제하지 않는 정책을 유지한다.

실제 CDF는 삽입 2,818,705건, 수정 전 44건과 수정 후 44건이었다. 수정 전후의 청취 키 집합이 같았고, 그중 5개 사건을 직접 추적해 Silver에 각각 한 행만 남은 것을 확인했다. 같은 곡의 다른 시각 청취는 별도로 보존됐다. 서로 다른 MSID가 같은 곡인지는 이번 검수 범위에 포함되지 않는다.

전수 검증 결과와 표본 검수 JSON 및 원본 사본 해시 증거는 결과 경로에 보존했다. 임시 Docker 볼륨과 절전 방지 도우미는 정리했다. Gold는 실행하지 않았다.


### 월별 Silver 전환 사전 실측 (2026-10-19)

현재 결과를 교체하지 않고 고정 Silver v3에서 사용자 이름 + recording_msid + UTC listened_month로 집계했다. 월은 도착 시간이 아닌 청취 시각 기준이다. 261개 월이 포함되며 월별 play_count 합계는 기존 상세 157,351,363건과 같다. 저장 후 Parquet를 다시 읽어 행 수와 합계를 확인했고 원본 상태도 변하지 않았다.

| 구성 | 행 수 | 활성 데이터 파일 바이트 |
| --- | ---: | ---: |
| 기존 Silver 상세 | 157,351,363 | 13,658,853,786 |
| 기존 사용자+MSID 전체 횟수 | 44,261,553 | 1,719,781,115 |
| 제안 월별 횟수 | 80,563,985 | 2,908,129,807 |
| 별도 곡 메타데이터 변형 사전 | 23,965,606 | 2,015,329,072 |
| 보존할 품질 격리 | 1,318,299 | 164,466,402 |

월별 사실 표는 상세보다 48.8% 작아진다. 기존 상세와 전체 횟수 및 격리의 합계 15,543,101,303바이트를 월별 횟수와 사전 및 격리 5,087,925,281바이트로 대체하면 약 67.3% 절감된다. 사전까지 포함한 새 전체 행 수는 105,847,890개다. 기존 전체 횟수 표를 추가로 유지하는 구성은 아니다. 기존 파일을 지우지 않았으므로 실제 디스크 여유가 이만큼 늘었다는 뜻은 아니다.

사전은 MSID, 곡명, 아티스트명, recording MBID, artist MBID 배열, MBID 출처의 서로 다른 조합을 보존했다. MSID마다 한 행으로 임의 선택하지 않았다. 이는 정답 곡 매핑이나 모든 출처 이력을 보존하는 표가 아니며 향후 메타데이터 귀속 규칙이 필요하다. 상세 삭제 뒤에는 Silver만으로 개별 청취 시각을 복원할 수 없으며 Bronze에서 재계산해야 한다. 월별 자료만으로 정확한 일별 및 주별 청취자 수를 만들 수 없다.

user_id를 쓰면 월별 80,563,570행으로 이름 기준보다 415행 적다. 이름 16개가 여러 ID에, ID 30개가 여러 이름에 연결된다. 월 안에서도 여러 ID에 연결된 이름+월 조합은 204개다. 두 식별자를 동일한 사람 식별자로 단정하지 않으며 이번 요구에 맞춘 주 수치는 사용자 이름 기준이다.

파일은 DuckDB 4스레드, 메모리 상한 8GB에서 월 파티션, Snappy로 썼다. 이름 기준 집계 65.77초와 쓰기 81.15초로 약 2분 27초였다. 별도 ID 기준 집계 및 쓰기는 228.84초, 메타데이터 준비 및 쓰기는 224.10초였다. ID 기준 전체 측정 단계 합계는 460.70초다. 캐시와 실행 순서가 달라 두 키의 속도 우열을 뜻하지 않는다. 운영 Delta 작성과 추가 검수를 포함한 전환은 10-20분을 잠정 예상하지만 아직 실측하지 않았다. 새 증분 로직 구현과 회귀 테스트 시간은 이 예상에 포함하지 않는다.

증분 최소 상태 설계는 아직 구현하지 않았다. 거대한 사건별 처리 이력 표 대신 Bronze를 사건 원장으로 유지하고, 집계와 같은 Delta 커밋에 Bronze 표 ID, 처리 버전, 품질 정책 버전과 집계 키 버전을 남긴다. 변경 덤프에서 사건 키인 사용자 이름+청취 시각+MSID를 추린 뒤 고정 Bronze 이전 및 이후 버전에서 해당 키 후보를 조회한다. 각 버전에서 품질 판정 후 기존 결정 규칙으로 승자를 고르고 월별 기여 차이만 반영한다. 같은 사건의 재도착은 차이 0, 새로운 시각의 청취는 +1, 삭제는 -1이며 승자 변경은 이전 기여를 빼고 새 기여를 더한다. 단순 덤프별 +1은 사용하지 않는다.

집계 변경과 체크포인트는 하나의 커밋으로 기록하고 단일 작성자 잠금이 필요하다. Bronze의 CDF 또는 변경 덤프 매니페스트와 이전/이후 버전 보존이 선행 조건이다. 현재 통합 Bronze에 CDF가 켜져 있다는 뜻은 아니다. 필요한 과거 버전이 사라지거나 원본 ID 또는 정책이 바뀌면 중단하고 명시적으로 재생성한다. Bronze 조회 비용은 아직 측정하지 않았다. 추가 덤프 각각이 전체 261개 월 중 251개 월을 건드려, 변경 월 전체 재계산은 기본 증분 방식으로 적합하지 않다.

이 수치는 시험 Parquet 활성 파일 기준이다. Delta 로그와 CDF, 실제 파일 배치 및 추가 메타데이터 컬럼에 따라 운영 저장량은 달라질 수 있다. 근거 JSON과 시험 파일은 flux-data/monthly-sizing-20261019에 보존한다. 운영 교체와 삭제 및 Gold 실행은 하지 않았다.

사전 평가 뒤 사용자 이름+MSID+UTC 청취 월을 주 단위로 하는 Silver를 별도 경로에 생성했다. 새 출력은 아래 세 표이며 개별 청취 상세나 기존 전체 기간 횟수 표를 복제하지 않았다.

| 표 | 행 수 | 활성 Parquet 바이트 | 파일 수 |

기존 상세+전체 기간 횟수+격리의 활성 파일 15,543,101,303바이트 대비 약 66.9%, 10,394,401,712바이트가 줄어드는 구성이다. 주 표의 행 수 감소는 48.8%다. 실제 Delta 출력은 약 5.15GB이며, 저장 엔진과 파일 배치가 다른 사전 Parquet 시험의 약 5.09GB와 구분한다. 로그, CRC 파일, 검증 중 임시 파일 및 보존한 이전 검증본은 이 활성 Parquet 비교에 포함하지 않는다. 기존 검증본을 지우지 않았으므로 호스트 디스크에서 이만큼 즉시 회수했다는 뜻은 아니다.

생성 단계는 월별 횟수 454.69초, 메타데이터 355.50초와 격리 33.09초로 합계 843.28초다. JVM 기동과 독립 검증 시간은 별도다. 로컬 CPU 상한은 처음 4개였으며 회귀 테스트와 병행할 때는 생성 2개와 테스트 2개로 총 4개를 유지했다. 운영 원본과 이전 검증본은 읽기 전용으로 사용했고 Gold는 만들지 않았다.

새 증분 경로는 Bronze의 이전/이후 사건 기여 차이를 반영하고 표별 커밋에 처리 버전을 기록한다. 보조 표의 무변경 MERGE에서 Delta가 커밋을 생략하는 실패를 중단 복구 테스트로 발견해, 실제 커밋이 없으면 처리 위치만 기록하도록 수정했다. 세 표의 처리 버전이 맞아야 완료이며 소비자는 잠금 안에서 확보한 표별 Delta 버전으로 읽는다. 사건별 영구 처리 표는 추가하지 않았다. 현재 통합 Bronze의 CDF는 비활성이므로 실제 다음 덤프 전 활성화와 이력 보존이 필요하다. 대용량 새 덤프 증분 속도는 이 초기 생성 결과로 대신하지 않는다.

기본 762개와 Spark 회귀 31개 및 별도 품질 정책 불일치 차단 1개가 통과했다. 소형 Spark에서 다른 덤프, 재실행, 삭제와 수정, 초기 및 증분 커밋 직후 중단 복구와 CDF 부재를 검사했다. 실제 전체 출력에도 같은 Bronze v0를 재실행했고 세 표가 모두 v0 그대로여서 새 커밋이 없었다. 근거는 flux-data/monthly-silver-20261019의 migration.json과 replay-audit.json에 보존한다.



독립 전수 대조도 완료했다. 월별 80,563,985개 키의 횟수 불일치, 중복 키와 잘못된 횟수는 모두 0건이며 play_count 합은 157,351,363이다. 메타데이터와 격리의 양방향 전체 차이도 각각 0건이다. 세 표의 CDF, Bronze ID 및 처리 버전, 30초 정책과 UTC 설정, 고정 원본 및 출력 불변 검사를 모두 통과했다. verification.json의 ok는 참이고 migration.json의 independent_validation_pending은 거짓이다.

독립 검증은 CPU 2스레드에서 849.07초였다. 생성 단계와 검증 단계 합계는 약 28분 12초로, 사전 예상 10-20분보다 길었다. 실행 당시 사전 양방향 비교는 원본의 DISTINCT를 두 번 계산하고 앞의 횟수 임시 표도 보유했다. 이후 재현 코드는 끝난 횟수 임시 표를 해제하고 사전 예상 결과를 한 번 계산해 재사용하도록 보완했으며 NULL과 배열, 출력 중복을 검사하는 테스트를 추가했다. 보완 코드로 대규모 검증 시간을 다시 측정한 것은 아니다. 이 최적화는 비교 규칙과 이미 끝난 검증 결과를 바꾸지 않는다.

최신 월별 결과는 flux-data/monthly-silver-20261019에 보존한다. 기존 운영 경로와 이전 검증본은 교체하거나 삭제하지 않았고, 월별 Gold는 실행하지 않았다.
