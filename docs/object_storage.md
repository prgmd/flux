# 오브젝트 스토리지 전환 (S3)

명세 9절은 `STORAGE_ROOT` 환경변수로 `file:///` ↔ `s3a://` 전환이
코드 수정 없이 되게 하라고 한다. 현재 어디까지 되어 있고 무엇이 남았는지의 기록이다.

## 왜 하는가

지금 데이터 루트는 이 노트북의 로컬 디스크다. 42GB를 쓰고 있고 1.7TB가 남아 있으므로
용량 때문에 옮길 이유는 없다. 옮기는 이유는 셋이다.

1. **경로 추상화가 실제로 되는지는 바꿔 봐야 안다.** 안 바꾸면 "된다고 생각하는 코드"만 남는다
2. 여러 대에서 같은 데이터를 읽으려면 로컬 디스크로는 안 된다
3. 클러스터를 늘리거나 줄일 때 데이터가 계산 노드에 묶여 있으면 곤란하다

## 되어 있는 것

`src/flux/common/config.py`가 URI 스킴을 다룬다. 테스트 12개가 붙어 있다.

```
FLUX_STORAGE_ROOT=s3a://flux-data
  storage_root : s3a://flux-data
  bronze       : s3a://flux-data/bronze/raw_listens
  is_local     : False
```

## 안 되어 있는 것

### ~~1. 잡들이 `config`를 거치지 않고 `pathlib.Path`로 경로를 만든다~~ (2026-09-07 해결)

```
원본         : s3a://flux-data
Path 통과 후 : s3a:/flux-data/bronze/raw_listens
```

`pathlib`은 연속된 슬래시를 하나로 접는다. 로컬 경로에서는 옳은 동작이고,
그래서 지금까지 아무 문제가 없었다. **URI에서는 스킴이 망가진다.**

**고쳤다.** 다섯 스크립트에서 `--root` 인자를 없애고 `FLUX_STORAGE_ROOT` 하나로
모았다. Spark에 넘기는 경로는 `config.bronze("raw_listens")`가 스킴을 유지한 채
만들고, 스테이징과 기록처럼 실제 파일이 필요한 곳은 `config.local_root()`를 쓴다.

같이 발견한 것: 로컬 경로 변환 함수가 7개 스크립트에 복사돼 있었고, 그 구현이
**`file:///data`를 상대 경로 `data`로 만들고 있었다.** 윈도우의 `file:///C:/...`
형태에서만 우연히 맞았다. 컨테이너에서는 그 함수를 거치지 않아 드러나지 않았다.
`config.local_root()` 하나로 모으고 드라이브 문자가 있을 때만 앞 슬래시를 떼도록 고쳤다.

고친 뒤 `bronze_stats.py`를 다시 돌려 **같은 수치가 나오는 것을 확인했다.**
경로 층만 갈렸고 동작은 그대로다.

> 여기서 배울 것: **추상화 층을 만들어 둔 것과 그것을 쓰는 것은 다른 일이다.**
> 층은 S0에서 만들었지만 이후 스크립트들이 그 층을 우회했다.
> 우회가 가능하면 우회하게 되고, 그러면 층이 있어도 효과가 없다.

### 2. 수급 단계는 로컬 전용이다

`fetch_incremental_range.py`, `extract_listens.py`는 `local_dir()`을 호출하고
로컬이 아니면 실패시킨다. 다운로드와 압축 해제가 일반 파일 입출력이기 때문이다.

이건 결함이라기보다 **경계**다. 원본을 받아 스테이징에 두는 일까지는 로컬에서 하고,
Bronze부터 오브젝트 스토리지에 두는 구성이 자연스럽다. 다만 그렇게 정했다고
적어 둬야 한다.

### 3. 실행 환경에 필요한 것들

- `hadoop-aws`와 AWS SDK jar. 지금 이미지에는 없다
- 자격증명 전달 방법. 환경변수, 인스턴스 역할 중 무엇을 쓸지
- S3A 커미터 설정. 기본 커미터는 이름 바꾸기에 기대는데 S3에는 이름 바꾸기가 없다

## 먼저 확인해야 할 것 — Delta의 ACID가 S3에서 성립하는가

이것이 가장 중요하고, **확인 전에는 옮기면 안 된다.**

강제 종료 실험에서 확인했듯 Delta의 ACID는 **트랜잭션 로그 파일을 원자적으로
만드는 것**에 기댄다. `_delta_log/00000000000000000035.json`을 쓸 때
"이미 있으면 실패"가 보장되어야 두 writer가 같은 버전을 덮어쓰지 않는다.

HDFS는 이 연산을 제공한다. **S3는 오랫동안 제공하지 않았다.** 그래서 Delta는
S3에서 writer가 하나뿐임을 전제하거나, 별도의 잠금 장치를 요구해 왔다.

현재 쓰는 Delta 버전이 어느 방식인지, 그리고 조건부 쓰기를 지원하는지는
**이 프로젝트에서 확인하지 않았다.** 문서를 읽고 끝낼 것이 아니라
Bronze에서 했던 것처럼 **적재 도중에 죽여서** 확인해야 한다.

지금 구성은 잡을 하나씩 돌리므로 writer가 하나다. 그 전제가 유지되는 한
문제가 없지만, **전제라는 것을 알고 있어야 한다.**

## 순서

1. 잡들이 `config`를 거치게 고친다 (로컬에서 먼저, 동작 변화 없음)
2. 로컬 MinIO로 `s3a://` 경로를 검증한다. AWS 비용 없이 같은 프로토콜을 쓴다
3. Delta의 로그 원자성을 강제 종료로 확인한다
4. 그다음에 실제 S3를 붙일지 정한다

**1번은 2026-09-07에 마쳤다.** 2~4번은 S4(스큐 실험)를 로컬에서 마친 뒤가 적당하다.

### 왜 S4 이후인가

로컬 클러스터는 워커 3개 × 2코어로 **의도적으로 6코어에 묶여 있다.** 그리고
워커가 한 호스트의 도커 브리지에 붙어 있으므로 **셔플이 실제 네트워크를 건너지 않는다.**

그래서 지금 재는 수치는 **네트워크 비용이 0에 가까운 조건의 기준선**이다.
그 기준선이 있어야 클라우드 수치에서 무엇이 네트워크 때문인지 갈라낼 수 있다.
기준선 없이 클라우드에서만 재면 "느리다"까지만 알고 왜 느린지는 모른다.

### 실제 AWS S3로 지금 옮기지 않는 이유

**컴퓨트가 이 노트북에 있다.** 스토리지만 AWS로 보내면 모든 읽기가 인터넷
이그레스가 된다. Bronze 한 번 전체 스캔이 24.76GB이므로 월 무료 구간(100GB)을
네 번이면 소진한다. S4는 파티션 수를 바꿔 가며 반복하는 단계라 훨씬 많이 읽는다.

비용보다 나쁜 것은 **측정 오염**이다. 처리 시간을 재는 실험에서 스토리지가
인터넷 건너에 있으면 회선 변동이 지배 요인이 된다.

**컴퓨트도 함께 올릴 때 옮긴다.** 같은 리전 안에서는 전송이 무료라 계산이 뒤집히고,
그때 비로소 노드를 늘리는 실험과 실제 셔플 네트워크를 잴 수 있다.

## 이름이 겹치는 문제

명세의 단계 이름 `S3`(Silver 정제)와 AWS S3가 겹친다.
이 문서에서 `S3`는 AWS를 가리키고, 단계는 **S3 스테이지**로 적는다.
