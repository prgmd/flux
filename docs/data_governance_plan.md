# 데이터 모델링과 품질 및 증분 운영 확장 계획

2026-10-22 계획 추가. 현재 구현과 측정값은 [상태 문서](status.md), 음악 식별과 승인 범위는 [검수 절차](recording_review.md)를 따른다. 이 문서는 앞으로 할 작업의 정본이며 도구 설치, CDF 설정 변경, 데이터 재생성 및 운영 승격을 완료했다는 뜻이 아니다.

## 목표와 현재 출발점

검증한 월별 Silver와 Gold를 바탕으로 모델 정의, 데이터 검사, 변경분 처리와 메타데이터 조회를 연결한다. 원천 수집은 일별 덤프 배치로 유지한다. CDC는 변경 데이터 캡처라는 접근이고 Delta CDF는 Delta 표의 변경 피드다. CDF를 활용하는 이번 범위는 버전 범위 기반 배치 증분이며 원천 실시간 수집과 구분한다. [Delta CDF 공식 문서](https://docs.delta.io/delta-change-data-feed/)

현재 통합 Bronze는 162,679,797행이며 월별 Silver는 사용자+MSID+UTC 청취 월 80,563,985행, play_count 합 157,351,363회다. 월별 및 연간 Gold 14개 스냅샷과 공식 귀속 분리 결과가 있다. 월별 증분과 중단 복구 코드는 있지만 문서에 기록한 전환용 통합 Bronze v0에는 CDF가 없으며 다음 실제 덤프의 대규모 증분 검증은 남아 있다. 기존 Gold는 DuckDB 배치와 불변 Parquet 스냅샷이다.

최근 곡 연결 표본은 102행, 후보 51쌍이다. agent의 실험용 승인 8, 분리 유지 2, 보류 41쌍과 사람 승인 0을 유지한다. 별도 사본의 138→137행 및 245회 보존 검증은 끝났지만 이 승인표는 운영 매핑이 아니다. 도구 도입 실험은 기존 검증 범위 또는 명시적인 sandbox 범위로 시작하며 사람의 전체 곡 검수 완료를 기다리느라 인프라 검증까지 멈추지 않는다. 승인 범위 확대와 전수 반영은 별도다.

### P0. 입력과 기대값을 고정한다

현재 검증본을 참조 입력으로 보존하고 작업 출력은 존재하지 않는 별도 경로에 둔다. Silver 세 표는 일관된 처리 상태에서 표별 버전을 고정하고 versionAsOf 또는 해당 버전에서 얻은 활성 파일 목록으로 읽는다. Delta 디렉터리의 모든 Parquet을 glob으로 읽지 않는다. Bronze 원본 ID와 버전, 공식 자료 지문, 기존 귀속 조사본과 승인 매핑 지문, 정책 및 코드 버전을 하나의 실행 문맥으로 기록한다.

대표 표본에는 정상 반복, MBID 없음, 같은 녹음의 여러 MSID, 한 MSID의 상충 근거, 피처링, Live와 Remix 및 Sped Up, 서로 다른 달의 같은 계정과 과거 청취의 늦은 도착을 넣는다. 기존 DuckDB 출력과 Python 독립 기대값을 기준으로 보관한다. 실제 사람 승인 0인 R9 매핑을 운영 입력으로 넘기지 않는다. 기존 Gold와의 동등성 실험은 기존과 동일한 귀속 정책을 사용하고 R9 확장은 별도 실험으로 구분한다.

현재 Python 3.14, Spark 4.2.0과 Delta 4.4.0, DuckDB 1.5.5 조합을 유지한다. dbt와 GX의 이 조합 호환성은 확인 전이다. 도구별 격리 환경에서 읽기, 검사, 문서와 산출물 생성까지 시험해 버전을 고정한다. 현재 dbt v2와 기존 v1 어댑터의 기능 및 산출물 차이도 확인한다. 특히 v2는 로컬 Parquet 등의 정적 분석 제한이 문서화돼 있으므로 설치 성공만으로 호환 완료 처리하지 않는다. [dbt DuckDB 연결과 제한](https://docs.getdbt.com/docs/local/connect-data-platform/duckdb-setup)

### P1. 품질 규칙의 정본을 만든다

규칙마다 ID, 대상 단계와 표, 검사할 버전 범위, 실패 또는 경고, NULL 허용, 측정값, 기대 조건과 예외의 근거를 기록한다. 기존 30초 판정의 기준값과 숫자 해석은 기존 코드가 정본이고 도구는 그 결과 및 일관성을 검사한다. Spark와 Python 판정 일치 테스트를 유지한다. 사람 승인과 도구의 검사 통과는 서로 다른 상태다.

| 규칙 후보 | 처리와 조건 |
| --- | --- |
| 사용자+MSID+UTC 월 키 중복, 필수 키 누락 | 실패 |
| play_count가 NULL, 비정수 또는 1 미만 | 실패 |
| 숫자로 해석된 ms_played가 30초 미만인데 유효 상세에 남음 | 정제 경계 실패, 재생 시간 없는 기록은 허용 |
| 원래 MBID가 없거나 곡 연결이 미확인 | 허용하고 상태 및 커버리지 기록 |
| 동일 입력의 곡 연결 전후 총 청취 수 불일치 | 실패, 사건 차감 정책 실험과 구분 |
| Gold 곡 청취 합과 Silver play_count 합 불일치 | 같은 입력과 정책 범위에서 실패 |
| 공식 참여 아티스트들의 청취 합이 전체보다 큼 | 정상 가능, 전체 합계 보존 검사를 적용하지 않음 |
| 청취자 수가 청취 수보다 큼, 비중이 허용 범위를 벗어남 | 정의된 분모와 빈 기간 처리에 따라 실패 |
| 연간 청취자 수를 월별 고유 수의 합으로 계산 | 여러 달의 같은 계정 표본으로 실패 재현 |
| 연결률, 격리율과 입력량의 급변 | 우선 경고, 기준 분모와 과거 분포를 재고 임계값 확정 |
| production 매핑에 사람 미승인 또는 오래된 근거 포함 | 실패, sandbox 판단과 분리 |

월별 Silver에는 개별 ms_played가 없으므로 30초 검사를 그 표에 억지로 적용하지 않는다. 보존한 상세나 Bronze 및 격리와 대조한다. 오래된 청취가 정상적으로 도착하므로 MAX(listened_at)만으로 수급 신선도를 판단하지 않고 덤프 도착과 적재 완료 시각을 사용한다. 검사는 전체 이관 시 전수, 이후 변경 범위 및 필요한 주기적 전수로 나누며 중복 스캔 비용을 측정한다. 품질 비율 임계값을 측정 없이 임의로 실패 기준으로 고정하지 않는다.

### P2. CDF를 준비하고 기존 증분 코드를 검증한다

먼저 별도 Bronze 사본의 실제 속성과 입력 이력을 확인한다. 이미 검증한 기준 버전과 월별 Silver를 고정하고 다음 덤프 쓰기 전에 CDF를 켠다. 활성화 전의 변경을 복원했다고 주장하지 않는다. 보존 기간은 예상 중단 및 복구 구간을 포함하도록 정하고 실험 도중 필요한 버전을 VACUUM으로 지우지 않는다. 검증 후 운영 Bronze에 같은 준비를 적용하는 절차를 따로 적는다.

`monthly_listens.changes`, `affected`와 `refresh`의 기존 경로를 재사용한다. CDF는 영향을 받은 사건을 찾는 데 쓰고 변경 행 수를 그대로 play_count에 더하지 않는다. 고정된 이전 및 이후 원본에서 품질과 동일 사건의 승자를 다시 구해 월별 기여 차이를 반영한다. 원본 ID와 마지막 처리 버전, 월별 표 및 사전과 격리 표의 처리 위치가 맞는지도 검사한다.

첫 실제 덤프, 같은 입력 재실행, 다른 비어 있지 않은 덤프와 재실행을 대조한다. 합성 사본에서는 수정 전후, 삭제, 계정이나 월 이동, 중복 재도착과 중간 중단을 주입한다. 매 시점 같은 Bronze 종료 버전에서 전체 품질 및 중복 규칙을 다시 계산하고 월별 모든 키의 횟수, 누락, 중복과 음수 여부를 비교한다. CDF 누락이나 원본 및 정책 변경 시 임의로 이어 가지 않는 동작도 검사한다. 스캔량과 실행 시간 및 최대 메모리는 실제로 측정한다. [CDF의 활성화 이후 기록과 이력 보존](https://docs.delta.io/delta-change-data-feed/)

### P3. Gold SQL을 dbt 모델로 옮긴다

대상은 `src/flux/gold/monthly_marts.py`의 집계 SQL이다. 수급과 Spark 정제, 공식 근거 어댑터, 승인 저널 및 월별 집계 코드는 유지한다. 별도 로컬 DuckDB 작업 공간에서 고정 Silver 및 검수 자료를 source로 등록하고 dbt의 ref 관계로 모델 순서를 나타낸다. source의 이름과 실제 스냅샷 및 승인 범위를 연결하는 입력 어댑터가 필요하다. dbt가 원래 Delta 파일 선택과 사람 승인을 알아서 해결한다고 가정하지 않는다.

우선 사용자별 월간 곡 집계→월별 곡 마트와 커버리지만 옮긴다. 같은 입력의 기존 결과와 모든 키 및 정수 횟수, 순위와 NULL 상태를 비교하고 부동소수 지표는 근거 있는 허용 오차로 대조한다. 이후 곡 사전과 귀속, 아티스트, 아티스트 내 곡, 버전, 계정 및 식별 커버리지와 연간 결과로 확대한다. 월별 및 연간 14개 기존 마트의 스키마와 의미를 보존한다. 전환 중 기존 생성기는 비교 기준으로 남긴다.

키 유일성, 필수값과 상태 집합, 참조 관계 및 집계 보존은 dbt 데이터 테스트로 옮긴다. 복합 키와 합계 보존은 사용자 정의 SQL 테스트를 사용한다. 열과 표 설명, 한 행의 단위, UTC 기간, 고유 계정과 참여 아티스트의 중복 귀속 의미를 함께 문서화한다. dbt 문서의 계보는 등록한 모델 범위이며 외부 Spark 처리와 저널 이력까지 자동 추적됐다고 표시하지 않는다. [dbt 데이터 테스트](https://docs.getdbt.com/docs/build/data-tests), [모델 문서](https://docs.getdbt.com/docs/build/documentation)

### P4. 실행 데이터 검사 도구를 붙인다

우선 후보는 Great Expectations의 GX Core다. Spark 경계에서 유효 및 격리 집계와 스키마를 검사하고 실행별 검사 결과와 Data Docs를 남기는 작은 실험부터 시작한다. 전체 데이터를 Pandas로 수집하지 않는다. Spark 4.2 및 Python과 검사 엔진의 호환성을 별도 환경에서 먼저 검증하고, 맞지 않으면 동등한 규칙을 실행할 수 있는 Soda의 SQL 경로를 대안으로 평가해 하나를 선택한다. 두 도구를 동시에 도입하지 않는다. [GX Core 워크플로](https://docs.greatexpectations.io/docs/core/introduction/gx_overview/), [Soda 지원 데이터 소스](https://docs.soda.io/reference/data-source-reference-for-soda-core)

정제 중 행별 판단과 격리는 기존 quality/build가 담당한다. dbt는 모델의 키, 관계와 집계 계약을 검사한다. GX는 단계 사이 데이터 상태와 프로파일 및 실행 보고를 담당한다. 공통 규칙 목록에서 각 검사의 실행 담당을 정하고 같은 수치를 여러 엔진으로 매번 전체 스캔하지 않는다. 일부 독립 오라클은 의도적으로 유지한다.

검사 결과에는 실행 ID, 입력 버전 및 정책, 규칙 ID, 관측값과 기대 조건, 심각도 및 실패 표본의 로컬 참조를 둔다. 계정 원문을 공개 보고서나 외부 서비스에 보내지 않는다. 키 중복과 횟수 변조 및 정제 누락을 일부러 넣어 오류 검출과 하류 중단을 확인한다. 경고는 결과에 남기고, 실패가 있으면 새 스냅샷의 completed 및 조회 대상 교체가 이루어지지 않게 한다.

### P5. Gold를 영향 기간 교체 방식으로 갱신한다

먼저 P3의 고정 입력 전체 재계산을 기준으로 둔다. Silver의 변경 전후 기여에서 영향을 받은 청취 월을 모두 수집하고 과거 월도 포함한다. 수정으로 월이 바뀌면 이전 및 이후 월과 연도를 모두 처리한다. 해당 월 전체의 순위를 다시 계산하며 특정 아티스트의 점수만 수정하지 않는다. 연간 청취자와 최대 계정 비중 및 집중도도 영향 연도의 사용자별 기록에서 다시 구한다. 월별 고유 수나 비중을 더하지 않는다.

dbt incremental 설정만으로 중복 가산 방지가 완성됐다고 보지 않는다. 영향 기간의 기존 결과를 교체하고, 입력 삭제로 없어진 키도 제거하는 방식을 작은 표본에서 검증한 뒤 채택한다. 모든 표에 대해 기존 전체 계산과 키별로 대조한다. 같은 입력 재실행, 마지막 행 삭제, 공동 순위, 피처링과 과거 도착, 실패 후 복구를 포함한다.

원본 변경과 정책 변경을 별도 트리거로 다룬다. CDF는 원본 행의 변화를 알리지만 같은 원본에서 승인 매핑, 아티스트 귀속과 버전 규칙만 바뀐 사실은 알려주지 않는다. 매핑 및 정책 지문과 영향 MSID 목록으로 관련 월과 연도를 다시 계산하고 범위를 특정할 수 없으면 새 전체 스냅샷을 만든다. 규칙 롤백도 같은 원칙으로 처리한다. 여러 모델의 성공은 하나의 원자적 커밋이 아니므로 전체 산출물 검사 후에만 완료 매니페스트를 확정하고 조회 대상을 바꾼다. 이전 스냅샷을 보존해 되돌릴 수 있게 한다.

### P6. 카탈로그와 운영 절차를 연결한다

첫 조회 수단은 P3의 dbt 문서다. 이후 OpenMetadata를 로컬의 제한된 실험으로 검토한다. 자산별 담당자, 원본 위치와 데이터 단위, UTC 시간 기준, 품질 규칙 및 최근 결과, 원본 및 매핑 버전, 갱신 시각, 미연결 처리와 가명화 범위를 등록한다. 표본 하나에서 Bronze→월별 Silver→Gold 경로 및 승인 매핑→곡 사전의 경로를 확인한다. 카탈로그에는 메타데이터와 로컬 근거 참조를 넣으며 전체 청취 원문이나 검수자의 승인 원본을 복제하지 않는다.

dbt 모델 문서와 의존 관계, 테스트 산출물의 수집은 선택한 dbt 및 OpenMetadata 버전 조합으로 검증한다. DuckDB와 파일 자산의 지원 여부를 먼저 확인하고 미지원 자산과 Spark 및 검수 저널 경로는 명시적 메타데이터 등록 또는 별도 연결을 설계한다. 이름과 경로만 등록해 자동 수집이나 열 단위 계보가 완성됐다고 주장하지 않는다. 공식 크레딧이나 개별 곡의 사람 승인은 기존 저널이 정본이다. [dbt 산출물 수집 계약](https://docs.open-metadata.org/v1.12.x/connectors/database/dbt/storage-configuration-overview), [용어와 자산 연결](https://docs.open-metadata.org/latest/how-to-guides/data-governance/glossary)

OpenMetadata의 공식 로컬 Docker 요구량은 최소 6GiB와 4vCPU다. 실제 노트북에서 메모리와 발열 및 동시 실행 비용을 재고 Spark 대형 작업과 동시에 돌리지 않는다. 해당 비용이 크면 dbt 문서 기반 카탈로그를 먼저 사용하고 서버형 확장 상태를 별도로 남긴다. [로컬 설치 요구사항](https://docs.open-metadata.org/latest/quick-start/local-docker-deployment)

최종 실행 흐름은 덤프 수신 및 검증→Bronze 적재→CDF 기반 Silver 갱신과 경계 검사→고정 입력 및 승인 범위 확정→dbt Gold→데이터 테스트와 독립 대조→새 스냅샷 확정→카탈로그 갱신이다. 중간 실패가 조회 중인 이전 결과를 깨뜨리지 않는지 확인한다. 먼저 단일 실행 명령의 재현과 재시작 절차를 갖추고 Airflow 통합은 후속으로 연결한다. 7일 연속 입력 및 재실행, 누락 기간과 처리 시간 및 저장량을 기록한 뒤 운영 검증 완료를 판단한다.

## 기존 정제 과제와 운영 승격의 조건

곡 연결과 공식 귀속 검수는 전 단계에서 별도 흐름으로 계속한다. MBID 없는 행의 임의 추론, 악센트 이름만 같은 연결, Live/Remix/Sped Up 통합은 하지 않는다. 다른 MSID 사이의 동일 시각 사건 차감은 상세 또는 Bronze에서 따로 판단하고 승인한다. 이 규칙을 채택하면 월별 Silver와 종속 마트의 재생성 범위를 다시 정한다.

계획 추가만으로 기존 새 경로 결과를 운영으로 바꾸지 않는다. 실제 승격 전에는 고정 입력과 승인 범위, 실패 주입 결과와 전체 또는 영향 기간 대조, 이전 스냅샷 복구 및 문서 갱신이 필요하다. 이번 문서 작업에서는 데이터와 환경을 바꾸지 않았다. PostgreSQL 서빙과 FastAPI, Kafka 및 원천 실시간 수집은 별도 후속 범위로 유지한다.
