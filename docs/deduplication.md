# 중복 제거 규칙

명세 6.3의 키는 `user_name` + `listened_at` + `recording_msid`다.
실측으로 확인한 것과 그 결과 정한 규칙이다.

근거: `measurements/2026-09-07-duplicates.md`,
`measurements/2026-09-14-duplicate-content-diff.md`.

## 확인한 것

| 항목 | 값 |
| --- | ---: |
| 지워질 행 | 4,521,025 (2.90%) |
| 키 컬럼의 빈 값 | 0 |
| 한 키의 최대 행 수 | 8 |
| 덤프를 걸친 중복 | 100% |
| 한 덤프 안의 중복 | 0 |
| 내용이 서로 다른 중복 키 | 310,285 (17.9%) |

**키는 그대로 쓴다.** 빈 값이 없어 모든 행에서 작동하고, 한 덤프 안에서
중복을 만들지 않으므로 키가 너무 느슨하지도 않다.

## 정해야 했던 것 — 내용이 다를 때 어느 쪽을 남기는가

82.1%는 완전히 같아서 아무 쪽이나 남겨도 된다. 17.9%는 다르다.

가장 단순한 규칙은 **"나중 덤프를 남긴다"**이고, 실제로 흔히 그렇게 한다.
재 보니 **틀렸다.**

| 나중 덤프의 필드 수 | 비율 |
| --- | ---: |
| 더 많다 | 2.5% |
| **더 적다** | **12.9%** |
| 같다 | 84.7% |

나중 것을 남기면 12.9%에서 필드를 잃고, **잃는 것의 대부분이 MBID다**
(`lastfm_artist_mbid` 262건, `lastfm_track_mbid` 29건, `lastfm_release_mbid` 18건).

반대로 앞의 것을 남기면 2.5%에서 잃는다. **어느 한쪽을 통째로 고르는 규칙은
둘 다 손해다.**

MBID는 dimension 연결의 유일한 수단이고 이미 64%가 없다
(`2026-09-14-mbid-shape.md` 기준 `NONE` 64.47%). 있는 것을 버리면 안 된다.

## 규칙

**MBID를 가진 쪽을 남긴다. 같으면 나중 덤프를 남긴다.**

정렬 기준을 순서대로 적으면 이렇다.

```
1. mbid_source 순위      MAPPING > CLIENT > LASTFM > NONE
2. artist_mbids 개수     많은 쪽
3. _source_dump          나중 것
4. _record_id            작은 쪽
```

각 단계의 이유다.

**1. `mbid_source` 순위가 먼저다.** 출처가 좋은 MBID가 있으면 그것을 살린다.
여기서만 `mbid_source`를 **순위로 쓴다.** 값의 의미는 여전히 출처 표시이고
(`mbid_resolution.md`), 순위는 **이 정렬에 한정된 판단**이다.
`MAPPING`은 ListenBrainz가 해석한 값이라 우선할 근거가 있고,
`CLIENT`와 `LASTFM` 사이에는 근거가 약하지만 **순서를 정해 두지 않으면
실행마다 결과가 달라진다.**

**2. 아티스트 MBID가 많은 쪽.** recording MBID가 같아도 아티스트가 다를 수 있다.
사라지는 필드 1위가 `lastfm_artist_mbid`였으므로 이 단계가 실제로 일한다.

**3. 나중 덤프.** 여기까지 같으면 최신을 택한다. `submission_client`가 22.9%에서
바뀌는데, 그때는 나중 값이 최근 상태를 반영한다.

**4. `_record_id`.** 마지막 못. 앞의 셋이 모두 같아도 **하나를 골라야 하고,
그 선택이 실행마다 달라지면 안 된다.**

> 4번이 없으면 같은 입력에 다른 결과가 나온다. 정렬이 안정적이지 않으면
> 두 행의 순서가 파티션 배치에 따라 바뀌기 때문이다.
> **멱등성은 Delta의 `replaceWhere`만으로 완성되지 않는다.** 같은 입력에서
> 같은 행을 고르는 것까지 결정적이어야 한다.

## 합치지 않는 이유

"두 행의 필드를 합쳐서 하나를 만든다"는 방법도 있다. 그러면 아무것도 안 잃는다.

**하지 않는다.** 두 가지 이유다.

1. **원본에 없던 레코드가 만들어진다.** Bronze의 `raw_json`과 대응되지 않는
   Silver 행이 생기고, 그러면 "이 행의 출처가 무엇인가"에 답할 수 없다
2. 필드마다 어느 쪽을 쓸지 또 정해야 한다. 규칙이 필드 수만큼 늘어난다

**잃는 것을 기록하는 편이 낫다.** 지워진 행 수와 그중 MBID를 가졌던 비율을
품질 지표로 남기면, 나중에 합치기가 필요해졌을 때 그 판단의 근거가 된다.

## 어디서 거르는가

**Silver 적재에서 거른다.** Bronze는 원본을 그대로 담는 층이므로 중복도 그대로 둔다.

Bronze에서 걸러 버리면 나중에 규칙을 바꿨을 때 **다시 만들 수 없다.**
원본 아카이브에서 재적재하면 되지만 그게 곧 "Bronze를 원본으로 믿지 못한다"는 뜻이다.

  나왔으므로 소수에 몰려 있는 것은 분명하지만, 전체 분포는 재지 않았다
