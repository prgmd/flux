# 연간 Gold 7개 마트의 dbt 고정 표본 검증

## 범위와 입력

2026-10-23에 연간 곡과 아티스트, 아티스트 내 곡, 버전, 계정, 전체 커버리지와 곡 식별 커버리지 7개를 추가했다. 월별 7개도 함께 다시 생성하고 대조했다. 성공 출력은 `data/dbt-yearly-20261023`다. 기존 [P0 고정 표본](2026-10-22-governance-baseline.md)의 월별 6,469행과 113,368회 및 곡 사전 344행과 라벨 100행, 공식 크레딧 46행을 그대로 복사했다. 새 연결이나 아티스트 귀속 승인을 추가하지 않았다.

기존 Python 3.11.9, dbt-core 1.11.16, dbt-duckdb 1.11.0 및 DuckDB 1.5.5의 분리 환경을 사용했다. 운영 Delta 경로 대신 실험 DB의 pinned 표 4개만 source로 등록했다. 원래 P0와 운영 데이터, 기존 월별 dbt 출력과 전체 Gold Parquet는 유지했다. dbt 모델은 staging 4개와 월간 및 연간 사용자별 뷰 6개, 최종 마트 14개로 총 24개다.

월별 7개와 연간 7개 모두 P0의 각 기간 기대 Parquet, 기존 SQL 생성기 및 Python 독립 집계와 일치했다. 모든 키와 컬럼, 자료형과 정수 및 NULL 상태를 비교했으며 실수는 상대 및 절대 허용 오차 1e-12를 적용했다. 모든 기간 합계와 사용자별 지표에서 불일치 0이며 같은 입력 재실행도 일치했다. 월별 결과의 행 수도 이전 [월별 확대 결과](2026-10-23-dbt-monthly.md)와 같다.

입력과 복사본 및 source 표 내용, 원래 P0 및 실행 프로젝트 지문은 유지됐다. `completed=true`, `production_applied=false`, `promotion_ready=false`다. 연간 전체 커버리지는 고정 표본의 22개 청취 연도를 포함한다.

## 월별 숫자를 합치지 않는 계산

int_user_yearly_songs는 월별 사용자+곡 키의 기여를 사용자+곡 키+UTC 연도로 합친다. 입력은 계정 정보가 남은 중간 표이며 월별 최종 마트의 집계값이 아니다. 연간 계정 수와 최대 기여 및 비중, 집중도와 유효 계정 수는 그 연간 사용자별 기여에서 다시 계산한다. 아티스트 및 버전도 같은 원칙을 적용한다. 연간 커버리지 계정 수와 곡 식별 상태별 계정 수도 해당 연도에서 다시 센다.

제어 표본은 9개 월별 행과 27회다. 한 계정이 두 달에 걸쳐 같은 곡을 듣고 다음 해에 다른 계정의 청취도 있다. 2026년 곡 r은 10회와 계정 2개, 최대 계정 9회와 비중 0.9, 집중도 0.82와 유효 계정 수 100/82다. 같은 곡의 월별 계정 수 합은 3이라서 연간 고유 수 2와 다르다. 2027년 같은 곡은 3회와 계정 1개로 별도다.

2026년 아티스트 a는 16회와 계정 3개 및 최대 한 계정 13회다. 곡 r의 아티스트 내 청취 비중은 10/16이며 계정 도달률은 2/3이다. 버전 unmarked는 17회와 계정 3개 및 최대 한 계정 13회다. u1의 연간 계정 지표는 13회와 고유 곡 2개 및 최다 곡 비중 9/13이다. 월별 곡 수 합은 3이므로 연간 고유 곡 수를 월별 합으로 만들지 않는다. 전체 커버리지는 24회와 계정 3개, 연결 청취 16회와 연결 계정 3개다. 곡 식별 matched_candidate 상태도 16회와 계정 3개다. Sped Up+Remix는 계속 구분한다.

## 테스트와 완료 조건

구현 전 빠른 검사에서 7개 통과와 13개 실패를 확인했다. 기존 비교기가 월별만 다뤄 기간별 14개 계약을 만족하지 못했다. 구현 뒤 tests/test_dbt_pilot.py의 20개가 통과했다. 월별 및 연간 기대 파일 14개를 복사하고 대조하는지, 연간 다섯 마트의 값 변조와 월별 청취자 수 합산 오류를 탐지하는지 포함한다. 관련 호스트 회귀는 테스트 파일 14개의 97개가 33.65초에 통과했다.

dbt build와 같은 입력 rebuild는 각각 모델 24개와 데이터 검사 145개가 성공했다. 169개 노드에서 실패와 경고 및 건너뛰기는 없었다. 연간 사용자별 기여는 월별 원천과 곡 사전에서 직접 계산한 값에 양방향 대조한다. 연간 곡 및 커버리지의 고유 계정 수와 각 마트 기여 및 순위, 비중과 집중도, 기간별 합계 보존도 검사한다. 다중 공식 크레딧이 있는 아티스트 합을 전체 청취 수와 같게 강제하지 않는다.

오류 주입은 기존 월별 10개에 연간 7개를 더한 17개 사본에서 모두 탐지됐다. 연간 곡 계정 수와 전체 계정 수를 월별 고유 수의 합으로 바꾸는 경우를 포함했다. 나머지는 연간 아티스트 최대 계정 횟수, 곡 비중, 버전 도달률, 계정 곡 수와 식별 상태 계정 수 오류다. 기대한 data test fail과 종료 코드 1을 확인했고 SQL 실행 error를 검출 성공으로 세지 않았다. 정상 DB 지문과 마지막 14개 마트 대조도 유지됐다. `drill_passed=true`, `scenarios_checked=17`, `canonical_database_unchanged=true`다.

실제 dbt 통합 pytest 1개는 제어 표본의 연간 계정 및 지표, 두 build와 문서 생성 및 오류 사본 17개를 확인했고 232.71초에 통과했다. 기본 호스트 검사와 분리했으며 Spark와 클러스터 또는 전체 저장소 테스트를 모두 실행한 결과는 아니다.

docs generate에서 source 4개와 모델 24개 및 최종 14개 마트의 직접 부모 관계와 컬럼 150개의 설명을 확인했다. index.html도 생성했다. 브라우저 렌더링과 외부 Spark 및 검수 저널의 자동 계보는 이번 범위가 아니다. 실행 시간은 debug 3.835초, build 13.527초, rebuild 13.679초, docs 9.654초였다. 전체 Silver 처리 시간으로 환산하지 않는다.

## 남은 범위

월별 및 연간 14개 마트의 고정 표본 이전을 완료했다. 전체 규모 생성과 성능, 기존 전체 결과 대조 및 운영 승격은 남아 있다. Gold 영향 기간 갱신과 GX 및 카탈로그 확장도 후속이다. 운영 Silver와 Gold 및 CDF 설정을 바꾸거나 곡 연결 정확성을 새로 확정한 결과가 아니다. 재현 방법은 [dbt 실행 문서](../dbt_pilot.md)를 따른다.
