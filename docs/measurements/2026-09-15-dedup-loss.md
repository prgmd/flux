# 중복 제거로 무엇을 잃었나 (2026-09-15)

`docs/deduplication.md`가 "합치지 않고 하나만 남긴다"를 고른 근거로 **잃는 것을
기록해 두면 나중에 판단할 수 있다**를 내세웠다. 그 기록이 없었다. 이제 잰다.

물어야 할 것은 지워진 행 수가 아니라 **지워진 행이 무엇을 들고 있었나**다.

## 전체

| 항목 | 값 |
| --- | ---: |
| 격리 뒤 행 | 155,713,649 |
| Silver 행 | 151,192,624 |
| 지워진 행 | **4,521,025** (2.9034%) |
| 적재 때 기록한 값 | 4,521,025 **일치** |
| 소요 | 673초 |

마지막 줄이 이 측정이 성립하는 근거다. 여기서 "제거 전"은 **지금 Bronze에서
다시 계산한 값**이고 "제거 후"는 **디스크에 있는 Silver**다. 두 시점이 어긋나면
뺄셈이 중복 제거 건수가 아니게 되므로, 적재 잡이 남긴 값과 대조한다.

## 출처별로 얼마나 지워졌나

| 출처 | 제거 전 | 제거 후 | 지워짐 | 그 출처 중 |
| --- | ---: | ---: | ---: | ---: |
| `MAPPING` | 29,562 | 29,562 | **0** | **0.00%** |
| `CLIENT` | 4,157,051 | 4,150,196 | 6,855 | 0.16% |
| `LASTFM` | 51,144,849 | 49,512,422 | 1,632,427 | 3.19% |
| `NONE` | 100,382,187 | 97,500,444 | 2,881,743 | 2.87% |

```
지워진 행 중 MBID를 갖고 있던 것 : 1,639,282  (36.26%)
```

## 36.26%는 혼자 보면 오해를 부른다

"지워진 행의 3분의 1이 MBID를 갖고 있었다"만 읽으면 많이 잃은 것처럼 보인다.
**출처별로 쪼개면 다르다.**

지워진 MBID 보유 행 1,639,282건 중 **1,632,427건(99.6%)이 `LASTFM`**이다.
MBID 출처 중 가장 신뢰도가 낮은 층이다. 나머지는 `CLIENT` 6,855건이고,
**ListenBrainz가 직접 해석한 `MAPPING`은 한 건도 지워지지 않았다.**

전체 MBID 보유율이 거의 안 움직인 것도 같은 이야기다.

| | MBID 보유율 |
| --- | ---: |
| 제거 전 | 35.53% |
| 제거 후 | 35.51% |

## `MAPPING` 0건이 규칙이 작동했다는 증거다

우연이 아니다. 남길 줄을 고르는 순서의 **첫 번째 키가 `mbid_source` 순위**다
(`MAPPING` > `CLIENT` > `LASTFM` > `NONE`).

그래서 한 중복 그룹 안에 `MAPPING` 행이 있으면 **반드시 그 행이 남는다.**
`MAPPING`에서 지워진 행이 0건이라는 것은 그 규칙이 실제 데이터 전체에서
한 번도 어긋나지 않았다는 뜻이다.

덤으로 하나 더 알 수 있다. **같은 그룹에 `MAPPING` 행이 둘 있었던 적이 없다.**
있었다면 하나는 지워져 0이 아니었을 것이다.

## 그래서 합쳤어야 했나 — 아니다

문서가 남겨 둔 질문에 이제 답할 수 있다.

합치기가 이득이 되려면 **지워진 행이 남은 행보다 나은 값을 들고 있어야** 한다.
그런데 정렬의 첫 키가 출처 순위이므로 **남은 행은 언제나 그 그룹에서 가장 좋은
출처를 가진 행**이다. 두 번째 키가 `artist_mbids` 개수이므로, 출처가 같다면
**아티스트를 가장 많이 가진 행**이 남는다.

즉 지워진 행이 남은 행보다 나은 MBID를 들고 있는 경우는 **규칙상 생기지 않는다.**
`MAPPING` 0건이 그 추론을 실물로 확인해 준다.

**합치면 얻는 것이 사실상 없고, 잃는 것은 있다** — 원본에 없던 레코드가 만들어져
Bronze의 `raw_json`과 대응되지 않는 Silver 행이 생긴다. 합치지 않기로 한
결정을 유지한다.

## 아직 재지 않은 것

- **지워진 `LASTFM` 행의 MBID가 남은 행의 MBID와 실제로 같은 값인가.**
  출처 층이 같아도 값이 다를 수 있다. 다르다면 "어느 쪽이 맞나"라는 다른
  질문이 생긴다. 여기서는 출처 층까지만 봤다
- **`_artist_count` 키가 실제로 몇 번이나 결정에 쓰였나.** 출처가 같아
  두 번째 키까지 간 그룹의 수는 세지 않았다

## 재현

```
docker run --rm -m 10g -v <데이터 루트>:/data \
  -e FLUX_STORAGE_ROOT=file:///data ... flux-spark \
  python scripts/investigations/measure_dedup_loss.py
```

결과는 데이터 루트의 `measurements/dedup-loss.json`에 있다.

적재 잡에 넣지 않고 따로 둔 이유는 이것이 **설계 판단을 위한 측정**이지 매번
볼 지표가 아니기 때문이다. Silver 재생성은 48분이 걸리고 이 측정만 11분이다.
