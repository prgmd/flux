# 2026-10-22 월별 곡 및 커버리지 dbt 대조

## 실제 표본과 대조 결과

성공 출력은 data/dbt-pilot-20261022-r3다. 운영 Delta 경로에 연결하지 않고 [고정 표본](2026-10-22-governance-baseline.md)을 복사한 로컬 DuckDB만 사용했다. [실행 절차](../dbt_pilot.md)에 따라 모델 7개와 데이터 테스트 37개를 실행하고 같은 입력에서 다시 실행했다. 두 build 모두 모델 성공 7, 테스트 통과 37, 실패와 건너뛰기 0이었다.

| 대상 | 행 수 | 단위 |
| --- | --- | --- |
| 고정 월별 입력 | 6,469 | 사용자+MSID+UTC 월 |
| 고정 곡 사전 | 344 | MSID |
| 고정 곡 라벨 | 100 | 기존 곡 키 |
| 고정 공식 크레딧 | 46 | 곡 키+아티스트 |
| 사용자별 월간 곡 | 6,241 | 사용자+곡 키+월 |
| monthly_song_metrics | 1,445 | 곡 키+월 |
| monthly_coverage | 255 | UTC 월 |

입력과 두 마트의 전체 청취 수는 **113,368회로 보존**됐다. 모든 키와 컬럼 및 자료형을 P0 기대 파일과 기존 SQL 생성기 및 Python 독립 집계에 각각 대조했고 불일치 0이었다. 순위와 NULL은 정확히 비교했으며 실수만 상대 및 절대 오차 1e-12를 허용했다. 곡 사전에서 recording MBID가 없는 31개 MSID도 유지했다. 이는 메타데이터 변형 행의 누락 수와 다른 단위다.

## 실제 실패 주입

정상 완료 DB를 복사한 별도 오류 사본에서 검사했다. 각 사본은 같은 DB 파일명을 사용해 기존 뷰의 카탈로그 참조를 보존한다. 원래 성공 DB와 고정 파일은 수정하지 않는다.

| 주입 | 기대 검사 | 결과 |
| --- | --- | --- |
| 월별 키 복제 | 월별 복합 키 유일성 | 실패 검출 |
| play_count를 0으로 변경 | 양의 정수 횟수 | 실패 검출 |
| 참조 곡 사전 삭제 | MSID 참조 관계 | 실패 검출 |
| listener_rank 변조 | 청취자 공동 순위 | 실패 검출 |
| 귀속 청취를 분모보다 크게 변경 | 커버리지 범위와 비율 | 실패 검출 |

5개 모두 기대한 dbt 데이터 테스트가 fail을 반환했고 명령은 종료 코드 1이었다. SQL 실행 오류를 예상한 실패로 오인하지 않도록 error 노드가 없는지도 검사했다. 소스 오류를 넣은 build에서는 관련 하류 모델이 건너뛰어졌다. 원래 성공 DB의 파일 SHA-256은 그대로였고 두 마트의 재대조도 불일치 0이었다.

## 제어 표본과 테스트

별도 pytest 통합 테스트는 여러 MSID가 같은 곡 키로 묶이는 경우, 한 계정의 반복과 공동 크레딧 2개, 미연결 곡과 MBID 누락 및 Sped Up+Remix를 넣었다. 1월 한 곡의 6회와 2계정, 최대 계정 5회를 확인했다. 전체 14회 중 연결 6회이며 크레딧이 둘이라고 12회가 되지 않았다. 고유 계정은 전체 3과 연결 2로 계산됐다. 청취자 수가 같은 두 곡은 같은 순위였고 조회에서는 곡명으로 정렬했다. 총 18회 보존과 동일한 오류 주입 5개도 통과했다.

입력 어댑터와 완료 제어의 빠른 테스트는 8개다. 변조 및 정책 불일치와 경로 중첩 거부, 원본 및 기대값 복사, 순위 및 source 변조 검출, 실패 명령의 완료 방지, 산출물 경로의 명시를 검사한다. 기존 품질 및 CDF와 고정 입력, Gold 및 검수 관련 호스트 회귀를 합해 197개가 12.13초에 통과했다. 별도 dbt 통합 pytest 1개는 실제 연결, 두 build와 문서 생성 및 5개 오류를 실행했고 76.31초에 통과했다. 전체 프로젝트 테스트 수와 구분한다. 기본 pytest에서는 dbt 표시 검사를 제외해 기존 가상환경에 dbt를 요구하지 않는다.

## 실행과 문서 산출물

분리 환경은 Python 3.11.9, dbt-core 1.11.16, dbt-duckdb 1.11.0, DuckDB 1.5.5다. debug 3.984초, build 8.353초, rebuild 8.649초, docs generate 7.263초였다. 각 명령은 초기화 비용을 포함하며 전체 데이터 처리 시간으로 환산하지 않는다. DuckDB는 스레드 2개와 2GB 메모리 설정을 사용했다.

문서의 모델 7개와 source 4개, 두 최종 마트의 부모 모델 및 22개 컬럼의 설명과 실제 카탈로그를 확인했다. index.html과 manifest.json, catalog.json 및 실행별 run_results.json을 로컬에 저장했다. Spark 및 원문 검수 저널의 계보는 이번 등록 범위 밖이다.

첫 실행은 두 마트가 일치했어도 미완료로 끝났다. 프로젝트 YAML의 로그 경로 Jinja가 그대로 폴더명으로 사용돼 실행 프로젝트 불변 검사가 잡았다. 경로를 명령 인자로 옮기는 과정에서 target-path가 전역 옵션이 아닌 하위 명령 옵션인 점도 확인해 실패 테스트를 보강했다. 전역 log-path와 build 및 docs의 target-path를 나누어 전달한 최종 실행에서는 프로젝트 복사본도 불변이었다. 앞선 실패 출력은 성공 기준으로 쓰지 않는다.

최종 상태는 completed=true, baseline_unchanged=true, inputs_unchanged=true, project_unchanged=true와 promotion_ready=false다. 운영 Silver 및 Gold와 CDF 설정은 변경하지 않았다. 나머지 월별 및 연간 마트와 Gold 증분, GX 및 OpenMetadata와 운영 승격은 아직 진행하지 않았다.
