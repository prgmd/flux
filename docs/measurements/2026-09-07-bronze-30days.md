# Bronze 30일치 적재 실측 (2026-09-07)

S2 게이트의 "최소 1개월분 적재를 완료하고 디스크 사용량을 기록한다"에 대한 결과다.

## 범위

| 항목 | 값 |
| --- | --- |
| 덤프 | 31개 (2026-08-08 ~ 2026-09-07) |
| 원본 파일 | `2026-8.listens`, `2026-9.listens` |
| 원본 줄 | 155,713,649 |
| Bronze 행 | 155,713,649 |
| 격리 행 | 0 |
| 대조 결과 | 31/31 통과 |
| 총 적재 시간 | 2,490초 (덤프당 평균 80초) |

하루 규모는 고르지 않다. 최소 2,023,136줄, 최대 9,027,470줄, 평균 5,023,020줄로
가장 많은 날이 가장 적은 날의 4.5배다.

서버는 증분 덤프를 30개만 보관한다. 그보다 오래된 것은 지운다.
증분으로 한 달을 넘겨 다루려면 매일 받아 두는 수밖에 없다.

## 디스크

| 항목 | 크기 |
| --- | --- |
| 원본 아카이브 (`tar.zst`) | 7.08GB |
| Bronze 활성 데이터 | 24.76GB (761개 파일) |
| Bronze 디스크 점유 | 27.09GB (831개 파일) |
| 회수 가능 | 2.33GB (9%) |

- 하루당 활성 데이터 **0.80GB**
- 압축 원본 대비 **3.50배**

Delta 버전은 35개다. 활성과 점유의 차이 2.33GB는 옛 버전이 참조하는 파일이고,
`VACUUM`으로 회수할 수 있다. 회수하면 그만큼 과거 버전을 읽을 수 없어진다.

차이가 커진 원인은 두 가지 재적재다. 하나는 ACID 확인을 위한 강제 종료 후 재실행,
다른 하나는 아래 결함을 고친 뒤의 재적재다. 평상시 적재만 하면 증가는 훨씬 완만하다.

## 적재 중 발견한 결함

9월 1일자 덤프에서 원본 4,173,539줄 중 11줄만 적재됐다. 대조 등식이 잡았다.

원인은 **덤프 하나에 파일이 둘**이라는 데 있었다. 달이 바뀌는 날의 증분 덤프에는
지난달 파일과 이번 달 파일이 함께 들어 있다. 적재는 파일마다 쓰기를 부르는데,
쓰기가 `replaceWhere _source_dump = '<덤프>'`로 범위를 잡으므로
두 번째 파일을 쓰는 순간 첫 번째 파일의 행이 통째로 지워졌다.

멱등성을 위해 넣은 장치가, 쓰기를 여러 번 하면 데이터를 지우는 장치가 된다.
파일을 모두 합쳐 **덤프당 한 번만 쓰도록** 고쳤다(`flux.bronze.merge.combine`).

한 달에 한 번만 드러나는 결함이다. 대조 등식이 없었으면 넘어갔을 것이다.

## 청취 시각의 범위

`listened_at`은 여전히 21.5년에 걸쳐 있다. 적재된 31일치 안에도 오래된 기록이 섞인다.
제출 시각과 청취 시각이 다른 시계라는 사실이 규모를 키워도 그대로 유지된다.

Silver와 Gold를 `listened_date`로 파티션하라는 명세는 이 분포를 전제하지 않는다.
S3 시작 전에 파티션 설계를 다시 봐야 한다.

## 재현

```
FLUX_STORAGE_ROOT=<데이터 루트> python scripts/fetch_incremental_range.py --days 30
FLUX_STORAGE_ROOT=<데이터 루트> python scripts/bronze_backfill.py --days 30
docker run --rm -v <데이터 루트>:/data -e FLUX_STORAGE_ROOT=file:///data \n  ... flux-spark python scripts/bronze_stats.py
```

덤프별 결과는 데이터 루트의 `measurements/bronze-<덤프>.json`,
집계는 `measurements/bronze-stats.json`에 있다.
