# user_id가 사용자를 안정적으로 가리키는가 (2026-09-14)

중복 조사의 표본에서 `user_name`은 같은데 `user_id`가 다른 경우가 많이 보였다.
사실이면 명세 5.3의 Gold 팩트가 `user_id`를 `dim_user` FK로 쓰는 설계가
성립하지 않으므로 전수로 확인했다.

대상은 Bronze 155,713,649행 전수다.

## 결과 — 안정적이다

| 항목 | 값 |
| --- | ---: |
| `user_id`가 없는 행 | 0 |
| 서로 다른 `user_name` | 38,854 |
| 번호가 둘 이상인 이름 | **7 (0.02%)** |
| 한 이름의 최대 번호 수 | 2 |
| 서로 다른 `user_id` | 38,844 |
| 이름이 둘 이상인 번호 | 17 (0.04%) |
| 한 번호의 최대 이름 수 | 2 |
| 한 덤프 안에서 번호가 갈린 (이름, 덤프) | **0** |

**`user_id`를 `dim_user` FK로 쓰는 설계는 문제없다.** 명세를 고칠 이유가 없다.

이름이 둘인 번호가 17개 있는 것은 **사용자가 계정 이름을 바꾼 경우**로 보인다.
번호가 그대로이고 이름이 바뀌었다는 뜻이므로, 오히려 `user_id`가
`user_name`보다 안정적이라는 증거다.

`dim_user`를 Type 1로 두라는 명세의 판단과도 맞는다. 이름 변경은 정정 성격이라
이력을 남길 필요가 없다.

## 표본이 틀렸던 이유 — `limit()`은 표본이 아니다

중복 내용 비교에서 400개 키를 이렇게 뽑았다.

```python
keyed.groupBy(*KEY).agg(...).filter(F.col("shapes") > 1).limit(400)
```

`limit()`은 **먼저 끝난 셔플 파티션에서 앞의 N개를 집어온다.** 셔플 파티션은
키 해시로 나뉘므로 그 400개가 **몇 명의 사용자에 몰린다.** 그중 하나가
번호가 갈린 7명에 속하면 표본의 대부분이 그렇게 보인다.

실제로 출력된 예시 3건 중 2건이 같은 사용자(`minivoodoo`)였다.

고친 방법은 **무작위로 섞은 뒤 자르는 것**이다.

```python
.orderBy(F.rand(seed)).limit(args.keys)
```

씨앗을 고정해 재현 가능하게 두었고, 표본에 사용자가 몇 명 들어왔는지를
함께 출력하도록 했다. 같은 편향을 다시 놓치지 않기 위해서다.
