명세 6.3의 품질 규칙 넷이 Bronze 155,713,649행에서 몇 건을 거르는지 쟀다.

최대값이 마지막 덤프가 만들어진 시각 언저리다. **미래 시각이 하나도 없다.**

## 규칙 4 — MBID 형식 위반은 한 자리에서만 40건

| 자리 | 있음 | 형식 위반 |
| --- | ---: | ---: |
| **`mbid_mapping.recording_mbid`** | 29,602 | **40 (0.1351%)** |
| `additional_info.recording_mbid` | 4,157,182 | 0 |
| `additional_info.lastfm_track_mbid` | 51,144,858 | 0 |
| `additional_info.lastfm_artist_mbid` | 57,328,649 | 0 |
| `additional_info.release_mbid` | 4,544,552 | 0 |
| `additional_info.lastfm_release_mbid` | 47,060,471 | 0 |

40건의 값은 전부 **빈 문자열**이다.

```
형식 위반 값의 실제 모습
  mbid_mapping.recording_mbid
        40회  ''
```

**클라이언트가 보낸 MBID는 하나도 안 깨졌고, ListenBrainz가 붙인 자리만 비어 있다.**
매칭에 실패했을 때 키를 지우는 대신 빈 값을 넣은 것으로 보인다.

`mbid.resolve`는 이미 맞게 처리한다. 빈 문자열은 UUID 형식이 아니므로
그 자리를 건너뛰고 다음 후보를 본다. **고칠 것이 없다는 확인이다.**

## 이 결과가 뜻하는 것

**격리 테이블은 비어 있게 된다.** Bronze의 격리가 0이었던 것과 같다.

규칙이 쓸모없다는 뜻은 아니다. **0은 기준선이다.** 나중에 0이 아니게 되면
원천이 바뀌었다는 신호가 되고, 그때 알아차릴 수 있는 유일한 장치가 이것이다.

다만 **이 데이터의 실제 품질 문제는 이 규칙들이 보는 곳에 없다.**

| 규칙이 보는 것 | 건수 | |
| --- | ---: | --- |
| 형식이 깨진 레코드 | 0 | 원천이 형식을 보장한다 |
| **MBID 없음** | **1억 38만 (64.47%)** | dimension에 못 붙는다 |
| **중복** | **452만 (2.90%)** | 임포터의 재전송 |

**형식은 성한데 내용이 부족하다.** 명세의 품질 규칙은 "깨진 입력"을 막는 장치인데,
이 원천은 깨진 입력을 주지 않는다. 실제로 거를 것은 **의미 수준의 문제**이고
그것은 `mbid_source` 분포와 중복률로 본다.

명세도 그것을 알고 있다. 6.3의 DQ 지표가 "`mbid_source` 분포와 `UNKNOWN`
클라이언트 비율을 매일 기록"이다. **규칙은 방어이고 지표가 관측이다.**
