# 워커 1개 강제 종료 — 재계산과 정합성 (2026-10-02)

명세 S4의 마지막 게이트다.

> 워커 1개를 강제 종료했을 때 재계산이 일어나고 결과가 정합한지 확인한다

**통과했다.** 실행기 하나가 끝내 둔 셔플 출력을 잃었고, Spark가 계보를 따라 **잃은 조각만**
다시 만들었으며, 결과 네 값이 기준선과 모두 같았다.

## 무엇을 돌렸나

| | |
| --- | --- |
| 클러스터 | standalone, 워커 3개(각 2코어 3GB). 실행기는 기본값 1g로 떴다(통합 메모리 456MB) |
| 작업 | 일별 아티스트 마트 집계(`mart_build.build`, salting 없음). 6,060만 행을 아티스트와 날짜로 묶는다 |
| 대조할 값 | 마트 행 수, 청취 합, 아티스트 수, 그리고 `(아티스트, 날짜, 청취)`의 해시 합 |
| 죽인 것 | `flux-spark-worker-2` 컨테이너, `docker kill` |
| 죽인 때 | 본 작업의 첫 셔플 단계가 끝나고 다음 단계가 돌던 순간 |

## 잃은 조각만 다시 만들었다

이벤트 로그에서 단계와 시도별로 태스크를 셌다.

| 단계 | 시도 | 계획 태스크 | 결과 | 무엇 |
| ---: | ---: | ---: | --- | --- |
| 3 | 0 | 569 | 569 성공 | 팩트 스캔과 부분 집계. 셔플 출력을 쓴다 |
| — | | | | **여기서 워커 2를 죽였다** |
| 5 | 0 | 25 | 성공 4, `FetchFailed` 7, `ExecutorLostFailure` 2 | 3번의 셔플을 읽는 쪽 |
| **4** | **1** | **190** | 190 성공 | **3번과 같은 셔플을 다시 만든다** |
| 5 | 1 | 21 | 21 성공 | 아직 못 끝낸 것만 다시 |

- 죽은 실행기의 셔플 블록을 가지러 간 태스크가 `FetchFailed`로 실패했다. 셔플 출력은 그것을
  쓴 실행기의 디스크에 있으므로, 실행기가 죽으면 **이미 끝난 맵 태스크의 결과도 같이 사라진다**
- Spark는 그 셔플을 만드는 맵 단계를 다시 제출했는데, **569개 전부가 아니라 190개만** 돌렸다.
  569의 3분의 1, 정확히 죽은 실행기가 맡았던 몫이다. 살아 있는 두 실행기의 출력은 그대로 썼다
- 받는 쪽(5번)도 이미 성공한 4개는 다시 하지 않고 남은 21개만 돌렸다
- 4번이 시도 1로만 보이는 것은 AQE가 쿼리 단계를 따로 잡으로 제출하기 때문이다. 잡 시작
  이벤트에 이렇게 찍혀 있다. 잡 2가 3번(569 태스크)으로 셔플을 만들고, 잡 3은 같은 569 태스크짜리
  맵 단계를 4번으로 5번의 부모로 들고 있다. 출력이 이미 있으니 4번은 건너뛰었고, 출력을 잃자
  시도 1로 제출되어 잃은 190개만 돌았다

이것이 계보(lineage) 기반 장애 복구다. 데이터프레임은 결과가 아니라 "어떤 입력에서 어떤
변환으로 나왔는가"라는 계산 방법이라, 중간 결과를 잃으면 그 조각만 입력부터 다시 계산한다.
체크포인트를 찍어 두는 방식과 대비된다. 다시 만들 수 있으면 저장할 필요가 없다.

## 재계산 대가 1.49배를 어떻게 읽나

308.1초에서 206.7초를 빼면 101초다. 두 가지가 섞여 있다.

- **다시 한 일.** 가장 무거운 스캔 단계의 3분의 1(190 태스크)과 받는 쪽 21 태스크
- **줄어든 일꾼.** 워커를 되살리지 않았으므로 죽인 뒤로는 6코어가 아니라 4코어로 돌았다

이 둘을 이번 측정으로는 가를 수 없다. 1.49배는 "워커 하나를 잃고 끝까지 간 비용"이지
"재계산만의 비용"이 아니다.

## 이 판정을 믿을 수 있는 이유

처음 짠 판정은 결과 네 값이 같은지만 봤다. 그러면 잡이 끝난 뒤에 죽였거나, 죽인 워커가
맡은 일이 없었어도 통과가 찍힌다. 그래서 두 가지를 더 했다.

**재계산이 일어났는지를 이벤트 로그로 센다**(`flux.common.eventlog.recovery`). 사라진 실행기,
그 실행기가 끝낸 태스크 수, 실패한 태스크와 다시 돈 단계다. 셋이 다 있어야 통과다. 기준선에서는
셋 다 0이었다.

**죽이는 시점을 사람이 아니라 규칙이 정한다**(`scripts/experiments/kill_worker_mid_shuffle.py`,
`flux.common.sparkui.ready_to_kill`). 드라이버 UI의 REST API로 단계 상태를 보다가 **100MB 이상의
셔플을 남기고 끝난 단계가 있고 다음 단계가 도는** 순간에 죽인다. 하한을 둔 이유는 Delta가
테이블을 읽기 전에 트랜잭션 로그로 파일 목록을 만드는 일도 셔플을 쓰기 때문이다(이 데이터에서
약 21MB). 하한이 없으면 본 작업이 시작하기도 전에 장부 단계 뒤에서 죽이고, 장부만 다시 만든
것을 재계산이라고 부르게 된다.

죽인 순간의 상태도 남겼다.

```
끝난 셔플 단계 [3]
도는 단계      [5]
실행기   2 172.18.0.3   끝낸 208  도는 1   ← 죽인 워커의 실행기
실행기   1 172.18.0.4   끝낸 209  도는 2
실행기   0 172.18.0.5   끝낸 208  도는 1
```

## 처음 돌렸을 때 죽은 이유

이 스크립트는 처음 돌린 날 기준선에서 `ARITHMETIC_OVERFLOW`로 죽었다. 해시 합을 `long`으로
더했는데 64비트 해시 1,479만 개의 합은 `long` 범위를 넘는다. Spark 4는 ANSI 모드가 기본이라
넘치면 멈춘다. ANSI가 꺼진 Spark 3이었다면 조용히 감겨서 그럴듯한 숫자가 나왔을 것이고, 두
실행이 같은 방식으로 감기니 대조도 통과했을 것이다. 지금은 `decimal(38,0)`로 더한다
(`flux.gold.mart_build.fingerprint`).

## 이 결과의 한계

- **한 번 돌렸다.** 같은 시점, 같은 워커다. 다른 단계에서 죽이면(예: 맵 단계 도중) 실행 중이던
  태스크만 다시 도는 다른 모양의 복구가 나온다
- **재계산 비용과 일꾼 감소를 가르지 않았다.** 위 절 참고
- **외부 셔플 서비스를 쓰지 않는 구성이다.** 셔플 서비스가 있으면 실행기가 죽어도 워커 노드의
  서비스가 블록을 계속 내주므로 이번처럼 맵 출력을 잃지 않는다. 다만 이번처럼 워커 노드 자체가
  죽으면 서비스도 같이 죽는다
- **단일 물리 기계다.** 워커는 컨테이너이고, 죽인 것은 프로세스지 기계가 아니다

## 재현

```
docker compose up -d spark-master spark-worker

./scripts/spark_run.sh -m 6g --name flux-worker-kill --network flux_default -p 4040:4040 \
  -v "$PWD/docker/spark-conf/spark-defaults.conf:/opt/spark/conf/spark-defaults.conf:ro" \
  -e FLUX_SPARK_MASTER=spark://spark-master:7077 \
  -- python scripts/experiments/experiment_worker_kill.py --phase baseline

# 위와 같은 명령에 --phase killed 를 주고, 다른 창에서
PYTHONPATH=src venv/Scripts/python scripts/experiments/kill_worker_mid_shuffle.py \
  --container flux-spark-worker-2

docker compose up -d spark-worker      # 죽인 워커를 되살린다
```

결과는 데이터 루트의 `measurements/worker-kill-baseline.json`, `worker-kill-killed.json`,
죽인 순간의 상태는 `worker-kill-trigger.json`, 이벤트 로그는 `eventlogs/worker-kill-{baseline,killed}/`.
