# Delta 파일 배치와 압축 실측 (2026-09-19)

명세 6.5의 세 줄이다.

    Delta OPTIMIZE 전/후        파일 개수, 조회 시간
    Z-Order 적용 전/후          특정 아티스트 필터 쿼리 시간
    압축 코덱 snappy vs zstd     파일 크기, 읽기/쓰기 시간

대상은 `gold.mart_daily_artist` 14,792,567행이다. 조회는 **가장 많이 나오는
아티스트 하나를 거르는 것**으로 잡았다. 드문 값을 고르면 어떤 배치에서도
파일 하나만 읽어 차이가 안 보인다.

## 배치 비교

같은 원본에서 사본 셋을 만들어 각각 다르게 뒀다. `OPTIMIZE`의 목표 파일
크기는 32MB로 낮췄다(기본 1GB).

| 배치 | 활성 파일 | 크기 | 필터 조회 | 다시 쓰는 데 |
| --- | ---: | ---: | ---: | ---: |
| 쓴 그대로 | 29 | 612.7MB | 2.43초 | — |
| `OPTIMIZE` | 28 | 615.7MB | 2.35초 | 18.18초 |
| **Z-Order** | **18** | **112.6MB** | **0.76초** | 21.96초 |

두 번 돌렸고 **크기와 파일 개수는 소수점까지 같았다.** 결정적인 값이라
흔들리지 않는다. 조회 시간은 1차에서 1.54초 → 0.97초, 2차에서 2.43초 →
0.76초로 **절대값은 달랐지만 방향이 같았다.**

### `OPTIMIZE` 단독은 아무것도 안 했다

파일이 29개에서 28개로 하나 줄었고 크기와 조회 시간이 그대로다.

작은 파일 문제가 **없었기 때문**이다. 마트가 612MB인데 파일이 29개라 하나에
21MB씩이고, 목표 32MB에 이미 가깝다. 합칠 것이 없으면 합쳐도 얻는 것이 없다.

> `OPTIMIZE`는 **작은 파일이 많을 때** 듣는 기법이다. 걸기 전에 파일 크기
> 분포를 봐야 한다. 여기서는 Silver와 팩트를 달 단위로 파티션해 둔 것이
> 이미 조각을 적당한 크기로 만들고 있었다.

### Z-Order는 크기를 5.4배 줄였다

612.7MB가 112.6MB가 됐다. **이것이 조회가 빨라진 주된 이유다.**

Z-Order를 data skipping 기법으로만 알고 있었는데, 실제로는 **압축률이 먼저
개선됐다.** `artist_mbid`로 정렬하면 같은 값이 이웃하게 되고, Parquet이
컬럼마다 쓰는 사전 인코딩과 런렝스 압축이 훨씬 잘 듣는다.

값이 흩어져 있으면 사전이 커지고 런이 짧아 거의 못 줄인다. 뭉쳐 있으면
"같은 값 N개"로 접힌다.

그러니 **읽을 바이트가 5분의 1**이 되고, 거기에 data skipping이 더해진다.
파일이 18개로 나뉘어 있으므로 범위에 안 걸리는 파일은 열지 않는다.

**쓰기를 비싸게 하고 읽기를 싸게 하는 거래**가 여기서는 분명히 남는 장사다.
한 번 21.96초를 치르고 조회마다 1.7초를 아낀다. 마트처럼 한 번 쓰고 여러 번
읽는 표에 맞는다.

## 압축 코덱 — 크기는 zstd, 시간은 판정 불가

| 코덱 | 크기 | 쓰기 | 전수 읽기 |
| --- | ---: | ---: | ---: |
| snappy | 612.7MB | 28.02초 | 1.80초 |
| **zstd** | **318.2MB** | 19.34초 | 3.19초 |

**크기는 zstd가 확실히 이긴다.** 절반이고, 세 번 재는 동안 값이 같았다.

**시간은 말할 수 없다.** 세 실행의 읽기 시간이 이렇다.

| 실행 | snappy | zstd |
| --- | ---: | ---: |
| 1차 | 2.03초 | 1.31초 |
| 2차 | **4,071초** | 1.20초 |
| 3차 | 1.80초 | 3.19초 |

**방향이 뒤집힌다.** 1~3초를 재는데 실행 간 편차가 그만큼이다.

2차의 4,071초는 측정이 아니라 사고다. 그 실행이 밤에 돌았고 머신이 중간에
절전에 들어간 것으로 보인다. **통제하지 못한 변인이 시간대였다.**

반복을 늘리거나 더 큰 데이터로 재면 가릴 수 있다. 다만 **크기가 절반이라는
확실한 이득이 이미 있으므로** 시간 차이를 확정하는 값이 크지 않다고 판단해
여기서 멈춘다.

## 결론

- **Z-Order를 쓴다.** 크기 5.4배, 조회 3.2배. 두 실행에서 방향이 같았다
- **`OPTIMIZE` 단독은 지금 이 표에 필요 없다.** 작은 파일 문제가 없다.
  파티션을 더 잘게 나누거나 증분 적재가 잦아지면 다시 볼 일이다
- **zstd를 쓴다.** 크기 근거만으로 충분하다. 저장 비용과 네트워크 전송이
  줄고, 오브젝트 스토리지로 옮기면 그 이득이 더 커진다

## 재지 않은 것

- **Z-Order를 여러 컬럼으로 걸었을 때.** `artist_mbid` 하나로만 했다.
  `(artist_mbid, listened_date)`처럼 둘을 걸면 각각에 대한 효과가 나뉜다
- **압축 코덱의 시간 차이.** 위에 적은 대로 편차에 묻혔다
- **Z-Order의 유지 비용.** 데이터가 덧붙여질 때마다 다시 걸어야 하는데,
  증분 적재를 아직 안 해 봐서 그 주기와 비용을 모른다
- **더 큰 표에서의 동작.** 마트가 1,479만 행으로 팩트(1억 5,180만)의 10%다

## 재현

```
docker run --rm -m 10g -v <데이터 루트>:/data \
  -e FLUX_STORAGE_ROOT=file:///data ... flux-spark \
  python scripts/experiments/experiment_delta.py
```

약 10분. 결과는 데이터 루트의 `measurements/delta-experiment.json`에 있다.

## 곁가지로 걸린 것 둘

**폴더 크기를 재고 있었다.** `OPTIMIZE`는 새 파일을 쓰고 옛 파일을 **로그에서만**
지우므로 디스크에는 둘 다 남는다. 폴더를 `rglob`으로 세니 612MB가 1,297MB로,
Z-Order 뒤에는 1,982MB로 **늘어나는** 결과가 나왔다. 트랜잭션 로그를 읽어
활성 파일만 세도록 고쳤다(`flux.common.deltalog`).

**Z-Order를 잴 수 없는 순서였다.** 처음엔 한 사본에 `OPTIMIZE`를 걸고 그 위에
Z-Order를 걸었는데, 기본 목표 크기가 1GB라 `OPTIMIZE`가 **파일을 1개로 합쳐
버렸다.** data skipping은 파일이 여럿일 때 건너뛰는 기법이라 하나면 잴 것이
없다. 사본을 따로 만들고 목표 크기를 32MB로 낮춰 다시 쟀다.
