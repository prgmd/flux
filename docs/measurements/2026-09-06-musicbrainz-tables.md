## 3. S3 차원 설계에 주는 함의

**`recording`이 4,000만 행으로 압도적이다.** 나머지 넷을 합쳐도 1,700만 행이다.

| 관점 | 판단 근거 |
|---|---|
| `dim_artist` (SCD Type 2) | 300만 행. 이력을 쌓아도 감당 가능한 규모다 |
| `dim_recording` | **4,000만 행.** 여기에 SCD2를 적용하면 이력이 급격히 불어난다 |
| 조인 전략 | listens와 붙일 때 `recording`이 가장 큰 쪽이다. 스큐 실험(S4)의 후보다 |

명세 5.3은 `dim_recording`도 차원으로 두는데, **SCD2를 어디까지 적용할지는 S3에서 다시 판단해야 한다.** 아티스트 이름은 바뀌어도 녹음 제목은 거의 바뀌지 않으므로, 이력 추적의 가치가 다르다.

## 4. mbid_mapping과의 관계

증분 덤프 실측(2026-09-04)에서 `mbid_mapping` 존재 비율이 **0.02%**였다. 즉 청취 기록에는 MusicBrainz 식별자가 거의 붙어 있지 않다.

이 덤프의 `artist`, `recording`이 그 매핑을 직접 만들어야 하는 재료다. 트랙명과 아티스트명 문자열로 4,000만 행에서 후보를 찾는 작업이 S3에 놓인다.

## 5. 측정 방법

`scripts/inspect_musicbrainz.py`. `tarfile`의 스트리밍 모드(`r|bz2`)로 압축을 풀지 않고 읽으며, 테이블마다 개행 수를 세어 행 수를 구한다.

- 마지막 줄에 개행이 없는 경우를 따로 더한다
- 요청한 테이블을 다 세면 즉시 멈춘다. 7GB를 끝까지 풀 이유가 없다
- 결과는 데이터 루트의 `measurements/musicbrainz-20260905-002519.json`에 남는다
