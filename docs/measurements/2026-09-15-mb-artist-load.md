# silver.mb_artist 첫 적재 (2026-09-15)

MusicBrainz 릴리스 `20260905-002519`의 다섯 표를 엮어 `silver.mb_artist`를 만들었다.

## 대조

| 항목 | 값 |
| --- | ---: |
| 원본 `artist` | 2,976,554 |
| 적재된 `mb_artist` | **2,976,554** |
| 추출 시간 (호스트) | 118초, 430MB |
| 적재 시간 (Spark) | **28초** |

행 수가 정확히 일치한다. 조회 표를 left join으로만 붙였으므로 행이 늘거나 줄지 않는다.

조회 표는 전부 브로드캐스트했다. 가장 큰 `area`가 12만 행이고 나머지는 258, 6, 5행이라
297만 행을 셔플할 이유가 없다. 28초가 그 결과다.

| 항목 | 행 | 비율 |
| --- | ---: | ---: |
| 지역은 있는데 국가가 아님 | **354,700** | **11.92%** |

`area_name` 49.69%와 `country` 37.78%의 차이가 이 값이다.

`artist.area`를 그대로 `country`에 넣었으면 **35만 4천 행에 도시나 주가
국가 자리에 들어갔을 것이다.** `iso_3166_1`을 거친 판단이 실제로 일했다.

그리고 **틀린 줄도 몰랐을 것이다.** `Greccio`도 `Canada`도 둘 다 문자열이라
타입 검사에 안 걸리고, 집계를 내야 "국가 목록에 이상한 게 섞였다"가 보인다.

## SCD Type 2 설계에 걸리는 것

명세 5.3의 `dim_artist`는 SCD Type 2다. 아티스트가 개명하거나 활동을 끝냈을 때
**과거 청취를 당시 이름으로 조회**하기 위한 구조다.

그런데 이력 추적의 대상이 될 값들이 대부분 비어 있다.

| 컬럼 | 채워진 비율 |
| --- | ---: |
| `begin_date` | 20.17% |
| `end_date` | **5.22%** |
| `country` | 37.78% |

`name`과 `sort_name`은 100% 차 있으므로 **이름 변경 추적은 성립한다.**
SCD2의 주된 목적이 그것이므로 설계는 유지한다.

다만 `country`나 `type`이 바뀌어 새 버전이 생기는 경우는 드물 것이다.
**이력이 몇 개나 쌓일지는 다음 릴리스를 받아 비교해야 알 수 있다.**

## 부분 날짜를 채우지 않았다

`begin_date`가 연도만 있는 경우가 흔하다. 1월 1일로 채우면 **없던 정밀도를
지어내는 것**이고, 나중에 "1월생 아티스트가 유난히 많다"는 가짜 패턴이 나온다.

있는 만큼만 문자열로 적었다.

```
1969          연도만 아는 경우
1969-05       연월까지
1969-05-03    온전한 날짜
```

날짜 타입이 아니라 문자열인 이유가 이것이다. 날짜 타입은 **정밀도를 표현할 수 없다.**

## 적재 중 걸린 것 — 컬럼 이름 충돌

첫 실행이 이렇게 죽었다.

```
[AMBIGUOUS_REFERENCE] Reference `gender` is ambiguous, could be: [`gender`, `gender`]
```

`artist`에 `gender`가 **숫자 FK로 이미 있는데** 조회 표의 이름 컬럼에도
같은 이름을 붙였다. 조인한 뒤에는 둘 중 어느 쪽인지 알 수 없다.

조회 표의 출력에 `_` 접두어를 붙여 원본과 겹치지 않게 하고, `select`에서
최종 이름으로 바꿨다. `type`과 `area`도 같은 이유로 함께 바꿨다.

> Spark가 **실행 전에 잡아 준 경우**다. 컬럼 이름 충돌은 분석 단계에서 걸리므로
> 데이터를 읽기 전에 죽는다. 조용히 한쪽을 고르지 않는 설계가 여기서 값을 했다.
